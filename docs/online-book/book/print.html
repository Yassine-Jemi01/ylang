The YLang Book

Welcome to The YLang Book, the official online guide to the YLang programming language, its compiler, and its tools.

This book is organized as a guided course and a technical reference. You can read it from the beginning to learn the language step by step, or use the chapter sidebar and search to jump directly to a feature. Code examples are copyable, the appearance can be changed, and previous/next navigation helps you move through the chapters.

The online edition is the canonical book. It is maintained alongside the compiler and its reference documents, so corrections can be published without maintaining a separate PDF edition. The tutorial explains how to use YLang; the reference chapters describe exact syntax, supported behavior, and known restrictions.

Which version does this book describe?

This edition documents YLang 2.2.0, the current stable release at the time of writing. The project is also developing YLang 2.3.0; its development notes, release gates, and pre-release checklist describe unreleased work and do not change the stable version.

The stable core uses explicit types and the default C-backend workflow. Some features added around the core are experimental and have narrower support:

  • HTTP requests and environment-variable access have documented runtime and security limits.
  • The source-aware terminal debugger and performance harness are tools for development and investigation.
  • Structs, enums, named imports, GUI/Game2D, the NASM backend, native Windows support, and YSPM packaging have feature-specific restrictions.
  • The NASM backend does not support every program accepted by the C backend.
  • YLang does not claim Rust-level memory safety and does not provide a security sandbox.
  • `Option` and `Result<T, E>` remain design proposals, not supported language constructs.

Always check the relevant reference chapter before depending on an experimental feature in a project. A construct being accepted by one compiler stage does not guarantee that every backend supports it.

Introduction

YLang is a compiled programming language designed around readable source code, explicit types, and compiler diagnostics that help you locate mistakes. The compiler is written in C17. Its default workflow checks a `.yl` source file, translates it to C, and invokes GCC or Clang to produce a native executable.

This book is both a tutorial and a technical reference. You will start with a small command-line program, learn how declarations and functions are organized, and then explore the compiler, standard library, optional graphical helpers, and platform-specific workflows.

What YLang is

YLang source code is written in `.yl` files. A program describes values and operations using the language’s own syntax. Before a native executable is produced, the compiler checks the source and reports issues such as syntax errors, unknown names, invalid assignments, and type mismatches.

The default backend generates C, so a compatible C compiler is part of the normal build process. GCC and Clang are the supported choices exposed by the command-line interface. Generated C can also be emitted for inspection when debugging a compiler issue or learning about the compilation process.

YLang also contains experimental extensions and tools. These include a restricted NASM backend, structs and enums, imports, GUI/Game2D helpers, HTTP and environment APIs, a terminal debugger, and optional Linux packaging. Each extension has its own support boundaries; the existence of a feature does not mean it is equally supported by every backend or platform.

What YLang is not

YLang is not an interpreted language, and the default compiler workflow is not an independent machine-code backend: it relies on GCC or Clang after generating C.

YLang is also not a complete systems language with every advanced feature available. In particular:

  • `Option` and `Result<T, E>` are design proposals, not current language constructs.
  • The experimental NASM backend supports a narrower subset than the C backend.
  • GUI/Game2D requires additional native dependencies and a graphical session for live-window testing.
  • Native Windows support is experimental and does not promise complete feature parity.
  • YLang does not claim Rust-level memory safety or provide a security sandbox.

These distinctions are important when deciding whether a feature is appropriate for a real project. This book labels experimental functionality and links to its contract or design document wherever possible.

Stable core and experimental extensions

YLang 2.2.0 is the release described by this edition. The stable core and its default C-backend workflow form the compatibility baseline. Extensions may change or have restrictions that do not apply to the stable core.

When choosing a feature, follow this checklist:

  1. Read the relevant tutorial to understand its intended use.
  2. Open the corresponding reference or specification for exact syntax.
  3. Check platform and backend support.
  4. Build and run a small example in the same environment you intend to use.
  5. Keep a minimal reproducer if the compiler behaves differently than expected.

Do not infer runtime behavior from syntax alone. A program that passes one stage of compilation may still fail during native compilation, linking, or execution.

How to read examples

Most tutorial examples are small on purpose. They isolate one idea so that you can change a value, run the compiler again, and observe what changes. Unless a chapter says otherwise, commands assume that you are in the root of the cloned YLang repository and that the compiler has already been built at `build/ylang`.

Shell commands and YLang source serve different purposes:

  • Shell commands such as `make` build the compiler or invoke it.
  • YLang code belongs in a `.yl` source file.
  • Output shown after running a program is an example of the program’s behavior, not another command to type.

If you see a mismatch between an example and the implementation, use the Complete Language Specification and report the smallest example that reproduces the problem.

Where to go next

If you have not built the compiler yet, continue to Install YLang. If you already have a working build, go straight to Your First Program. For an exact list of accepted syntax, keep the Complete Language Specification nearby.

Install YLang

This chapter explains how to build the YLang compiler from source, verify the build, and prepare the optional dependencies used by graphical examples. Building from source is the most direct way to use the compiler version documented by this book and run the project’s regression tests.

Before you begin

You need:

  • Git to download the source repository.
  • GCC or Clang with C17 support to compile the YLang compiler and the C it generates.
  • GNU Make to run the project’s build and test targets.
  • A terminal in which you can run shell commands.

Linux and macOS are the primary documented development environments. A native 64-bit Windows path using MinGW-w64 is available, but it is experimental and has restrictions described in the Windows Setup guide.

GUI and Game2D examples have extra requirements: SDL2 development files and `pkg-config`. These are not required for ordinary command-line programs.

Linux

Fedora

Install the compiler toolchains and build tools:

```sh sudo dnf install gcc clang make git ```

Debian or Ubuntu

Install the equivalent packages:

```sh sudo apt update sudo apt install build-essential clang make git ```

Clone and build

Download the repository, enter its directory, and build the compiler:

```sh git clone https://github.com/Yassine-Jemi01/ylang.git cd ylang make ```

The resulting compiler should be located at `build/ylang`. If `make` fails, read the first compiler or linker error in the output; later messages may only be consequences of that first failure.

Run the regression tests:

```sh make test ```

A successful test run is a useful check that the compiler and its expected development dependencies are working. It does not mean every experimental feature works on every platform.

macOS

Install Apple’s command-line developer tools:

```sh xcode-select –install ```

Install GNU Make and the LLVM toolchain with Homebrew:

```sh brew install make llvm git ```

Use GNU Make as `gmake` when invoking the build and test targets:

```sh gmake gmake test ```

For GUI/Game2D programs, install SDL2 and `pkg-config` as well:

```sh brew install sdl2 pkg-config ```

The compiler’s normal C-backend workflow still needs a working C compiler. If a build cannot find GCC or Clang, verify that the compiler is installed and available on your shell’s `PATH`.

Windows

The experimental native Windows path uses 64-bit MinGW-w64 from an MSYS2 MINGW64 shell. MSVC is not the supported toolchain for this milestone.

Follow the Windows Setup guide for the exact package list, environment, and current limitations. Do not assume that a build tested on Linux will have identical support on Windows.

Verify the compiler

After `make` finishes, check that the compiler executable exists:

```sh ./build/ylang ```

The compiler’s help output should list the available commands. The everyday workflow is:

```sh ./build/ylang check path/to/program.yl ./build/ylang build path/to/program.yl -o program ```

Replace the example path with an actual `.yl` file. The first command checks the source; the second creates a native executable through the default C backend.

Optional: GUI and Game2D dependencies

On Fedora, SDL2 development files and `pkg-config` can be installed with:

```sh sudo dnf install SDL2-devel pkgconf-pkg-config ```

On Debian or Ubuntu:

```sh sudo apt install libsdl2-dev pkg-config ```

On macOS, use the Homebrew command shown above. If the graphical example fails to compile, verify that SDL2’s development files are installed and that `pkg-config` can find them. If it builds but no window appears, run it from a graphical desktop session; headless environments cannot validate live window behavior.

Optional: install a Linux package

YLang also publishes an optional `.yspkg` package for compatible Linux x86-64 systems using YSPM. This is a packaging option, not a replacement for the compiler toolchain required when building from source. See YSPM Linux Packages for package requirements and installation details.

Troubleshooting

  • `make: command not found`: install GNU Make, or use `gmake` on macOS.
  • `gcc` or `clang` is missing: install one of the supported C toolchains and check that it is available on `PATH`.
  • SDL2 is not found: install the development package, not only the runtime library, and confirm that `pkg-config` is installed.
  • A test fails: preserve the first failing test’s output and command. Do not treat a partial test run as a complete pass.
  • A program builds on one platform but not another: check the platform support page and the relevant backend contract before assuming the source is portable.

Your First Program

Create a file named hello.yl:

function main() -> int {
    let const string name = "YLang";
    print("Hello from", name);
    print("The answer is", 40 + 2);
    return 0;
}

The program defines the main function, creates a constant string, prints two lines, and returns an integer exit status.

Check, build, and run

From the repository root:

./build/ylang check hello.yl
./build/ylang build hello.yl -o hello
./hello

The first command checks the source without producing an executable. The second uses the default C backend and invokes a C compiler to build the native program. The final command runs it.

On Windows, the compiler executable is normally build/ylang.exe; the output program should use a Windows executable name such as hello.exe.

What if it fails?

Read the complete diagnostic, including its error code. Check punctuation, declared types, and the compiler command before changing the program. The Compiler Error Codes page explains stable diagnostic identifiers.

Try one change

Change the value of name, or replace 40 + 2 with a different integer expression. Run the same check/build/run sequence again. The point is to build a habit: check the source first, then compile it, then run the output.

The Compiler Workflow

The normal YLang workflow separates source checking from native compilation. A useful cycle is edit, check, build, run, and test. Keeping these stages distinct makes failures easier to locate: a source error is different from a missing C compiler, a linker failure, or a runtime problem.

1. Check before building

```sh ./build/ylang check hello.yl ```

Use `check` while editing. It asks the YLang compiler to validate the source and reports issues such as syntax, name, initialization, and type errors without building the final executable.

When a check fails, start with the first diagnostic. Record the file, line, column, error code, and complete message. Fix one cause at a time and run the check again; changing several unrelated things at once makes it harder to tell which change mattered.

A successful check means the source passed this compiler stage. It does not prove that a native compiler or linker will succeed, that every backend supports the same feature set, or that the program’s runtime behavior is correct.

2. Build a native executable

```sh ./build/ylang build hello.yl -o hello ```

The `-o hello` argument chooses the output path. The default backend emits C and invokes GCC or Clang. To select Clang explicitly:

```sh ./build/ylang build hello.yl -o hello –cc clang ```

The C compiler is part of this route: YLang does not yet have a complete general-purpose native backend independent of GCC/Clang. If the source check succeeds but the build fails, read the native compiler or linker output as well as the YLang diagnostic.

3. Run and verify the result

On Linux or macOS, run an executable named `hello` from the current directory with:

```sh ./hello ```

Compare the actual output with the behavior you intended. For nontrivial programs, test normal input, boundary values, and failure cases. A successful build only confirms that the compilation steps completed; it does not guarantee that the program is logically correct.

4. Inspect generated C

```sh ./build/ylang emit-c hello.yl -o build/hello.c ```

Generated C can help you understand the compilation pipeline or investigate a compiler issue. Use it as a debugging aid, not as a stable public interface unless a specific release explicitly guarantees the generated representation.

When inspecting output, ask a focused question: Was the source expression translated as expected? Is a function call missing? Did a value get converted before it was passed onward? If the generated C appears wrong, preserve the smallest YLang program that reproduces the issue and compare the result with the program’s expected behavior.

5. Assembly and the experimental NASM path

On supported Linux x86-64 systems, the compiler can emit assembly or build a program from the restricted NASM subset:

```sh ./build/ylang emit-asm examples/your-program.yl -o build/your-program.asm ./build/ylang build-asm examples/your-program.yl -o build/your-program ```

NASM is experimental. It does not support every construct accepted by the C backend, and unsupported combinations should be rejected explicitly. Do not assume that a successful C-backend build means the same source will build with NASM. Read the Backend Roadmap before choosing the assembly route for a project.

If a feature works with one backend but not the other, reduce the source to a minimal example and record which backend and compiler version you used. This makes backend-parity issues easier to reproduce.

6. Use the test suite

When working on the compiler itself, run the relevant tests after each change. The repository’s main regression target is:

```sh make test ```

For changes that affect code generation, backend parity, parsing, or runtime behavior, run the focused test as well as the broad suite when one is available. A test run is only a pass if it completes and reports success; a command that stopped early or skipped tests should not be described as a full pass.

7. Understand the failure stage

SymptomLikely stage to inspect
YLang syntax or type diagnosticSource checking
C compiler reports an errorGenerated C or native compilation
Undefined reference or missing libraryLinking and dependencies
Executable starts but gives wrong outputRuntime logic or code generation
C backend succeeds but NASM rejects the sourceExperimental backend support boundary
GUI builds but no window appearsRuntime environment or graphical session

These are starting points, not guaranteed diagnoses. Read the full error and reproduce the failure before deciding what caused it.

Summary

Use `check` for fast source feedback, `build` for the default native executable, `emit-c` to inspect the C translation, and the experimental assembly commands only when their limitations fit your project. For deeper implementation details, continue to Compiler Architecture.

YLanglings — Practice by fixing code

YLanglings is YLang’s offline, compiler-backed learning tool, inspired by Rustlings. Instead of only reading examples, you receive a small YLang program with an intentional mistake. Read the compiler diagnostic, edit the source, and verify your fix with the real YLang compiler.

YLanglings is part of the YLang 2.3 developer-experience scope. It is a companion tool rather than a compiler dependency.

Start locally

From the YLang repository root, install the local command:

make install-ylanglings PREFIX="$HOME/.local"

Then use it from any directory:

ylanglings list
ylanglings next
# After finishing the core track:
ylanglings next --optional
ylanglings run 01
ylanglings edit 01

Edit the displayed source file directly, or use ylanglings edit 01 to open it in your configured editor; then verify it:

ylanglings verify 01

If the compiler is not on PATH, pass its location:

ylanglings --compiler ./build/ylang verify 01

Use ylanglings hint NUMBER for a hint and ylanglings reset NUMBER to restore an exercise’s original broken starter. The list command shows progress, while next shows the first incomplete core exercise. Use next --optional to move through optional challenges. Use edit NUMBER to open it in your configured editor.

Learning path

The core track contains 16 exercises. It starts with program structure, variables and types, and mutability, then moves through conditions, loops, functions, arrays, structs, enums, strings, modules, f-string interpolation, explicit conversions, loop control, and text file I/O.

The optional track contains 10 challenges for nested loops, enum logic, struct functions, JSON parsing, Binary I/O, HTTP Streaming, terminal UI, Voice, JSON builders, and owned strings. Optional challenges are separate from core completion and are never required to finish the core track.

How verification works

For runnable exercises, YLanglings invokes the compiler’s check and build commands, runs the resulting program with a ten-second limit, and compares its output with the expected result. Progress is saved locally using an atomic file replacement. The tool does not need an internet connection, does not install third-party Python packages, and sends no telemetry.

Compiler check/build subprocesses have a 60-second timeout. Exercise programs are native executables and run with the current user’s permissions; YLanglings is not a sandbox, so review source before running it.

Some native API exercises are intentionally marked compile-only. They verify that the compiler accepts the documented API signatures; they do not pretend to exercise a native audio, GUI, or terminal device. Runtime behavior for those integrations belongs to the compiler’s dedicated integration tests.

ylanglings verify-all is a maintainer-only command available from the source checkout, where the private solutions/ directory is present. It checks all 26 reference solutions, collects failures, and never writes learner progress. The repository’s make test target runs both the CLI contract tests and this full curriculum verification. The normal user installation deliberately omits reference solutions.

YLanglings is a learning aid, not a replacement for the compiler regression suite, security review, or sanitizer tests. It verifies only the behavior specified by each exercise.

Program Structure

A YLang source file uses the `.yl` extension. The language makes types visible in declarations and function signatures, and most command-line programs define a `main` function that returns an integer status.

This chapter introduces the pieces that appear in many programs: functions, local variables, constants, expressions, control flow, and user-defined data. For exact grammar and compiler-specific restrictions, use the Complete Language Specification.

A complete small program

```ylang function add(int left, int right) -> int { return left + right; }

function main() -> int { let int total = add(20, 22); print(total); return 0; } ```

The first function accepts two integer parameters and returns their sum. The `main` function calls it, stores the returned value, prints it, and returns a status code. Breaking behavior into small functions makes it easier to name the purpose of each operation and test it separately.

Functions and signatures

A function declaration includes its name, parameter list, return type, and body:

```ylang function is_positive(int value) -> bool { return value > 0; } ```

The parameter’s type describes what the function expects. The return type after `->` describes the value callers receive. When changing a function signature, check every call site: callers must pass compatible arguments and use the returned value correctly.

Use the compiler to confirm the exact syntax accepted by your version. Do not assume that a feature from C, Python, Rust, or another language is available merely because its syntax looks familiar.

Local variables

A mutable local uses a declaration such as:

```ylang let int score = 10; score = score + 1; ```

The declared type is `int`; the next statement reads the current value, adds one, and assigns the result back to the same binding.

A constant declaration uses `const`:

```ylang let const string language = “YLang”; ```

Initialize a local before reading it. A constant cannot be reassigned after its declaration. Prefer constants when a value should not change, because this communicates intent to readers and prevents accidental reassignment.

Expressions and statements

An expression computes a value. Examples include an integer literal such as `42`, a variable name such as `score`, and an arithmetic expression such as `score + 1`. A statement performs an action, such as declaring a variable, assigning a value, calling a function, or returning from a function.

Keep expressions small while learning. If a diagnostic points to a long expression, split the calculation into named intermediate values; that makes the types and the source of a mismatch easier to see.

Control flow

Conditional statements and loops let a function choose and repeat work. A condition should have the type required by the language, and expressions in the body must obey the same type and initialization rules as expressions elsewhere.

When learning a control-flow construct:

  1. Start with the smallest program that uses it.
  2. Check the program before adding more behavior.
  3. Try a boundary case, such as a condition that is false immediately.
  4. Inspect the output and any diagnostic rather than guessing what the construct means.

Consult the Complete Language Specification for the supported grammar and exact restrictions.

User-defined data

YLang 2.x includes experimental structs and unit enums. Structs group named fields into a single value; enums represent one of a declared set of variants. These features are useful for modeling small domains, but their limits and backend support are not the same as Rust’s.

Continue to Structs and Enums and Matching for the actual contracts. In particular, verify support for a feature in the backend and platform you plan to use instead of assuming every accepted construct is portable.

Common mistakes

  • Missing a declaration: declare a local before using its name.
  • Wrong type: compare the declared type with the expression’s type and use only documented explicit conversions.
  • Reassigning a constant: use a mutable declaration if the value genuinely needs to change.
  • Assuming familiar syntax: check the language specification for the exact form accepted by YLang.
  • Treating a design proposal as shipped: proposals and roadmaps describe intent; the implementation and release documentation define current support.

Practice

  1. Change the example so that `add` adds different integer values, then check and run it.
  2. Add a constant string describing the result and print it alongside the total.
  3. Deliberately assign a value of the wrong type, read the complete compiler diagnostic, and then correct the declaration or expression.

Types and Explicit Conversions

YLang declarations make types visible. The language does not silently convert arbitrary values between types. This makes the intended representation visible in the source and helps the compiler identify incompatible operations before the program runs.

The exact type grammar and supported operations are documented in the Complete Language Specification. This chapter explains how to think about types and how to make conversions intentionally.

Common built-in types

The common built-in types include:

  • `int` for integer values.
  • `float` for floating-point values.
  • `bool` for boolean values.
  • `char` for character values.
  • `string` for text.

Choose a type based on the value’s meaning, not only on what makes an assignment compile. For example, text that happens to contain digits is still text until you parse it into a numeric value. Similarly, a numeric result should not be treated as a string until it has been formatted.

Declare values with their types

A declaration states the type at the point where a value is introduced:

```ylang let int count = 12; let float ratio = 0.5; let bool enabled = true; let const string label = “items”; ```

These examples illustrate the purpose of typed declarations; use the specification and compiler to confirm the exact forms supported by the version you are using.

A type mismatch is not necessarily a compiler obstacle to work around. It may reveal that the program is mixing two different concepts. Before converting a value, ask whether the operation makes sense for the domain.

Convert intentionally

Use explicit conversion functions when you need a different representation:

  • `to_float(integer)` converts an integer to a floating-point value.
  • `to_int(float)` truncates toward zero and reports a runtime error for non-finite or out-of-range values.
  • `to_string(value)` formats supported scalar values as a string.
  • `string.is_int(text)` checks whether the full text is a valid signed integer representation.
  • `string.parse_int(text)` parses integer text with failure handling.

These functions make a conversion visible at the call site instead of hiding it inside an assignment or expression. Refer to the Complete Language Specification for the precise behavior and supported cases.

For example, when a program receives a string from a file or user input, do not assume it is a valid integer simply because it looks numeric. Validate or parse it using the documented API, and handle the failure path before using the result.

Truncation and numeric boundaries

Converting a floating-point value to an integer can discard the fractional part. The documented `to_int` behavior truncates toward zero, so it is not the same as rounding to the nearest integer. A conversion can also fail for values that are non-finite or outside the supported integer range.

When a calculation depends on a boundary, test values around that boundary and handle runtime errors as specified. Avoid relying on accidental behavior from a particular C compiler or platform.

Type errors are useful

When a value has the wrong type, use this process:

  1. Read the entire compiler diagnostic, including its error code and source location.
  2. Check the declared type of each value involved in the expression.
  3. Decide whether the declaration is wrong or whether the expression is combining unrelated types.
  4. If a conversion is semantically appropriate, use a documented conversion function explicitly.
  5. Run `check` again, then build and test the corrected program.

Avoid adding a conversion merely to silence an error if it changes the meaning of the calculation.

Not implemented in this release

`Option` and `Result<T, E>` have design notes but are not implemented language constructs in the release documented here. Refer to Option and Result Design for the proposal; do not use them as current syntax or assume that their proposed behavior is available.

Practice

  1. Declare an integer and convert it to a floating-point value using the documented function.
  2. Convert a numeric value to a string for display.
  3. Try parsing a valid integer string and an invalid one; observe how the documented API reports failure.
  4. Test a floating-point value with a fractional part to understand truncation toward zero.

Use the compiler and specification together: the specification explains the intended contract, while a minimal test confirms how the current build behaves.

Functions and Modules

Functions provide named units of behavior; imports let a source file use selected declarations from another `.yl` file. This chapter explains how to keep code organized as a project grows from one file to several.

Functions first

A function should have a clear purpose, a readable signature, and a body that performs a related set of operations. Parameters describe the values the caller supplies; the return type describes the value produced by the function.

```ylang function answer() -> int { return 42; }

function main() -> int { print(answer()); return 0; } ```

The caller uses the function’s name and parentheses to invoke it. If a function signature changes, check every caller for compatible arguments and return-value handling.

A local import

Given a sibling file named `math_tools.yl`:

```ylang function answer() -> int { return 42; } ```

A second file can import that function:

```ylang from “./math_tools.yl” import answer;

function main() -> int { print(answer()); return 0; } ```

Relative paths are resolved from the importing source file. The imported name becomes available to the importing source according to the module system’s current rules.

In this release, imports are experimental and do not imply a central package registry or dependency solver. Import aliases and qualified module namespaces are not part of the current contract.

Organize one module at a time

Keep each module focused on one coherent responsibility. A small math module, for example, can hold reusable calculations; the entry-point file can then coordinate input, calls, and output.

A practical workflow is:

  1. Create the new source file and add one small function.
  2. Import only the declarations the caller needs.
  3. Run `check` on the entry-point file after changing the import graph.
  4. Build and run the smallest example before moving more code.
  5. If the compiler reports a missing file or symbol, verify the spelling and the path relative to the importing file.

The compiler checks imported symbols and reports missing files or names; circular imports are rejected. Do not assume that an import has the behavior of a package manager or that it downloads dependencies.

Keep dependencies understandable

Prefer a simple, visible module graph. Avoid splitting a tiny example into many files before the boundaries are useful. When a module depends on another module, make that relationship explicit in the source and keep the imported API narrow.

For reproducible builds, keep the files required by the program together in the project and document any external native dependencies separately. YLang’s local import system is not a substitute for a dependency registry, version resolver, or system package manager.

Troubleshooting

  • The imported file cannot be found: check the exact relative path and file extension.
  • The imported function is unknown: confirm the exported declaration name and the import spelling.
  • A cycle is reported: restructure the modules so their dependency graph is not circular.
  • The project works in one directory but not another: review relative paths and the source file from which they are resolved.
  • A module feature is rejected: consult the Module System reference; do not assume aliases or qualified namespaces are supported.

For the exact grammar, visibility rules, and restrictions, read the Module System chapter.

Practice

Create a file with a function that returns a fixed integer, import it from a separate `.yl` file, and call it from `main`. Check the entry point, build the program, and run it. Then rename the imported function deliberately and inspect the compiler’s diagnostic before correcting it.

The Standard Library

YLang’s standard library provides built-in namespaces for common tasks. The available surface is defined by the implementation and its reference documents; do not assume that a similarly named function from C, Python, Rust, or another language exists in YLang or behaves the same way.

This chapter is an orientation guide. For exact function signatures, accepted argument types, error behavior, and backend support, consult the Complete Language Specification and the feature-specific references linked below.

Available namespaces

The current documentation covers namespaces such as:

  • `math` for supported mathematical operations.
  • `string` for string inspection and explicit parsing/conversion helpers.
  • `io` for console and file-related operations.
  • `path` for path-related checks.
  • `image` for supported image-related operations.
  • json for parsing, validation, typed field access, escaping, and formatting. The immutable raw-text builders are additions in the unreleased 2.3 development line; see JSON support.
  • `env.get(name)` for reading a process environment variable without launching a shell.
  • `http` for optional synchronous requests and bounded pull-based streaming through libcurl; see HTTP and API Requests and HTTP Streaming.
  • `terminal` for line-oriented console input/output, and `tui` for raw-key terminal applications; see Terminal UI.
  • `voice` for local audio playback and callback-backed HTTP stream playback through SDL2_mixer; see Voice and Audio Playback.

The namespaces do not all have the same maturity. Basic language operations and experimental additions should be evaluated separately. HTTP streaming, environment access, Voice/audio, and raw-key TUI are optional additions and are outside the stable-core compatibility guarantee.

Strings and parsing

Text values often arrive from files, console input, or network responses. Do not treat text as a number simply because it contains digits. Use the documented parsing and validation helpers when converting text into a numeric value.

The documented helpers include `string.is_int(text)`, which checks whether the full text is a valid signed integer representation, and `string.parse_int(text)`, which parses integer text with failure handling. Consult the specification for exact accepted formats and failure behavior.

When handling untrusted or user-provided text, validate the result before using it in arithmetic or as an index, path, or other control value. For JSON, use json.parse, typed getters, and json.last_error; use json.escape when inserting user-provided text into a JSON string. The immutable json.object, json.array, json.set, json.remove, and json.push helpers build raw JSON text without introducing a dynamic JSON value tree.

Files, paths, and environment

Use the documented `io` and `path` operations for file-related work instead of relying on the current working directory or hand-built path assumptions. Paths can be interpreted differently across platforms, so test the same operation on every platform your application claims to support.

The `env.get(name)` helper reads a process environment variable without launching a shell. Environment variables may contain missing, empty, or unexpected values; check the documented return behavior and validate the value before depending on it. Avoid storing secrets in source code or printing sensitive environment values to logs.

See Binary I/O for byte-oriented file access and its current limits. HTTP streaming can copy raw response chunks into reusable byte buffers with http.stream_read_buffer; do not use the text-only http.stream_read API for binary payloads. If a text chunk contains an embedded NUL byte, http.stream_read records a stream error, terminates that stream, and discards queued text bytes.

HTTP and API Requests (Experimental)

Status: experimental development feature for YLang 2.3. HTTP functions are implemented on the C backend behind an optional libcurl dependency. The API includes synchronous calls plus an initial asynchronous task API built on libcurl’s multi interface; async/await is currently restricted to HTTP task handles, not general-purpose YLang functions.

Streaming

Pull-based HTTP Streaming is implemented in the current 2.3 development tree. It provides a distinct http_stream handle, bounded 64 KiB per-stream response buffering, and a binary-safe byte-buffer read path. The Voice runtime can consume a stream through voice.play_stream. See HTTP-STREAMING.md for ownership, limits, and verification status; this feature is not part of a published release yet.

Requirements

Install libcurl development files and pkg-config only on machines that build programs using the HTTP namespace.

  • Fedora: sudo dnf install libcurl-devel pkgconf-pkg-config
  • Debian/Ubuntu: sudo apt install libcurl4-openssl-dev pkg-config
  • macOS: brew install curl pkg-config; if Homebrew curl is keg-only, set PKG_CONFIG_PATH="$(brew --prefix curl)/lib/pkgconfig:$PKG_CONFIG_PATH".
  • Windows with MSYS2 MINGW64: pacman -S mingw-w64-x86_64-curl mingw-w64-x86_64-pkgconf

The ordinary compiler and programs that do not call http.* do not require libcurl. ylang check validates HTTP calls without linking the HTTP runtime; native ylang build requires the development dependency when an HTTP function is used. The experimental NASM backend does not support HTTP calls, including streaming. Async tasks are process-local handles with a maximum of 32 in-flight slots; each task may be consumed once by await, and cancellation is not a remote rollback.

http_stream is a distinct handle type. http.stream_status and http.stream_headers wait until final response headers are available (including an allowed redirect chain), while leaving the response body unread. http.stream_read returns NUL-terminated owned_string chunks for text responses; if a chunk contains NUL, it returns an empty string, records an error in http.stream_error, terminates the stream, and discards queued text bytes. For arbitrary binary data, use http.stream_read_buffer(stream, buffer, max_bytes) with a root buffer from io.buffer_new(0); it overwrites the buffer and returns the exact byte count. This preserves embedded NUL and high-bit bytes. Passing a stream to voice.play_stream(stream) transfers ownership to the Voice runtime; do not use the stream handle again after handoff.

Pass headers as one header per line, separated by \n, for example "Content-Type: application/json\nAuthorization: Bearer ...". Header names are validated and malformed headers are rejected. A task handle has the distinct http_task type, so the compiler rejects await or http.cancel on arbitrary integers. Await each task at most once. Cancellation frees its pending request state; using a consumed handle again reports an error/false result rather than reusing stale memory. Use http.status() to distinguish HTTP error responses such as 404 from transport failures: an HTTP 404 response is still a successful HTTP transfer and its body is returned. http.response_headers() returns the final response’s headers as newline-separated lines, replacing intermediate response headers after redirects. http.request(method, url, body, headers) accepts only the uppercase methods GET, POST, PUT, PATCH, DELETE, or HEAD. Its body argument is used for POST/PUT/PATCH/DELETE; GET and HEAD ignore it.

Buffered responses are limited to 8 MiB. Streaming responses are not subject to that whole-body limit; each active stream uses a fixed 64 KiB body buffer (maximum 16 active streams). Buffered http.get/http.request and await task results are text strings: if a response body contains an embedded NUL byte, the string result is empty and http.last_error() explains that binary-safe streaming is required. Use http.stream_read_buffer with an io.buffer for arbitrary response bytes. Buffered HTTP requests use a 5-second connection timeout and a 15-second whole-request timeout. Streaming requests retain the 5-second connection timeout but have no whole-transfer timeout, so long audio recitations are not truncated by a fixed request deadline. Requests without custom headers automatically follow at most five redirects, restricted to HTTP/HTTPS. A Content-Type header is permitted through redirects regardless of the field-name letter casing; if the header list includes any other header, automatic redirect following is disabled and the original 3xx status, body, and headers are returned. This avoids forwarding arbitrary credentials such as Authorization or X-API-Key to a redirect target. HTTPS certificate and hostname verification are enabled; the runtime does not offer an insecure TLS bypass. These safeguards help with reliability, but they do not make arbitrary URLs safe in every application or create a network sandbox.

Reading API keys from environment variables

Use env.get(name) to read a process environment variable. It returns an empty string if the variable is missing; it never invokes a shell. Do not hard-code API secrets into examples, source control, or the compiler.

function main() -> int {
    let string api_key = env.get("MY_AI_API_KEY");
    if (string.length(api_key) == 0) {
        print("Set MY_AI_API_KEY before running this program.");
        return 1;
    }

    let string headers = string.concat(
        "Content-Type: application/json\nAuthorization: Bearer ",
        api_key
    );
    let owned_string response = http.post_with_headers(
        "https://api.example.com/v1/chat/completions",
        "{\"model\":\"example-model\",\"messages\":[{\"role\":\"user\",\"content\":\"Hello\"}]}",
        headers
    );

    print("HTTP status:", http.status());
    if (string.length(http.last_error()) > 0) {
        print("Request failed:", http.last_error());
        return 1;
    }
    print(response);
    return 0;
}

Replace the illustrative endpoint, model name, request JSON, and authorization scheme with those documented by the chosen provider. API response bodies are returned as strings. Use std.json to validate, parse, inspect, and format JSON documents; see JSON support. Object/array construction helpers are tracked separately for the 2.3 development milestone.

Error behavior

  • Invalid URLs and malformed headers return an empty owned string, set http.last_error(), and set status to zero.
  • DNS, TLS, timeout, connection, response-size, and other libcurl failures return an empty owned string and set http.last_error().
  • HTTP statuses such as 400, 401, 404, and 500 are not treated as transport errors. The response body and status are returned so the program can inspect them.
  • http.status() and http.last_error() describe the most recent HTTP operation in the current process; they are not per-request response objects.
  • Synchronous http.get/http.request calls block until the transfer completes. The request_async/await workflow allows several network transfers to progress concurrently, but await itself blocks the current thread while pumping libcurl. It is not a general scheduler and must not be described as non-blocking on GUI event loops. General async functions, structured task groups, and GUI/event-loop integration remain future work.
  • http.cancel(task) cancels a queued or in-progress request; cancellation is not a remote rollback and may happen after the server has received the request.

Progressive audio playback

The Voice runtime can take ownership of an HTTP stream and pass its bytes to SDL2_mixer through a custom forward-only SDL_RWops source:

function main() -> int {
    let owned_string url = terminal.read_line("HTTPS audio URL: ");
    let http_stream stream = http.stream_open("GET", url, "", "");

    if (!voice.play_stream(stream)) {
        print(voice.last_error());
        voice.shutdown();
        return 1;
    }

    while (!voice.is_finished()) {
        tui.sleep_ms(20);
    }

    print(voice.last_error());
    voice.shutdown();
    return 0;
}

Calling voice.play_stream(stream) transfers ownership of the stream to Voice, even if playback setup fails. Do not call http.stream_read, http.stream_read_buffer, http.stream_done, or http.stream_close on that handle after handoff. Voice closes the HTTP stream when playback is stopped, fails, or reaches EOF. Pause, resume, stop, and volume continue to use the regular voice.* functions.

The audio reader is forward-only; seeking is not implemented. Actual MP3 support depends on the installed SDL2_mixer codec build. The callback-backed reader and HTTP bridge require runtime tests before being treated as production-ready.

Current implementation limits

  • C backend and libcurl only; progressive audio additionally requires SDL2_mixer.
  • Each stream uses a fixed 64 KiB response buffer; the runtime applies libcurl pause/resume backpressure when the consumer falls behind.
  • At most 16 active streams.
  • The API is blocking and pull-based; it is not a general asynchronous scheduler.
  • A stream is single-consumer and must be closed. Process shutdown also releases active streams.
  • HTTP 4xx/5xx statuses are responses, not transport errors; inspect the status and read the body.
  • On transport failure, buffered response bytes remain readable first. http.stream_read_buffer then returns -1 once the buffer is drained; inspect http.stream_error for the specific failure. The text API returns an empty string at the end and uses the same per-stream error accessor.
  • Redirects and TLS verification follow the existing HTTP runtime policy. Connection setup has a 5-second timeout; the stream has no whole-transfer timeout so long recitations are not cut off after 15 seconds.

Binary-safe path: use http.stream_read_buffer(stream, buffer, max_bytes) with a root buffer created by io.buffer_new(0). Each call overwrites that buffer with the next raw bytes and returns the exact byte count. Embedded NUL bytes and values from 0 through 255 are preserved. The caller owns the buffer and must call io.buffer_free when finished. Slices are rejected as destinations.

http.stream_read remains a text convenience API and is not safe for arbitrary binary payloads. The binary buffer path is available. The Voice runtime is connected through voice.play_stream(http_stream): it consumes the HTTP stream incrementally through the callback-backed SDL_RWops reader and takes ownership of the handle. This bridge is implemented on the C backend, but an end-to-end HTTP-to-audio test and real MP3 playback validation are still required before calling it production-ready.

Verification

The loopback integration test covers delayed chunk delivery, partial reads, response metadata, empty bodies, 404 response bodies, and a 9 MiB transfer. These tests must pass in CI before the implementation is considered validated. TLS failure, timeouts, cancellation under load, concurrent streams, sanitizer coverage, and Windows/macOS runtime behavior remain separate verification gates.

Representation and behavior

The parser, accessors, and formatter are part of the documented 2.2 standard-library surface. Immutable object/array builders are additions in the unreleased 2.3 development line; do not assume they are available in a 2.2.0 installation.

JSON documents and extracted raw values are represented as owned strings, not as a dynamic YLang value tree. This keeps the first implementation compatible with the current type system and makes it useful for HTTP responses and configuration files. json.get and json.at return an empty string on lookup failure; typed getters return their zero value and set json.last_error(). Check json.has before accessing optional object properties.

json.stringify currently validates and copies an already-serialized JSON value. json.pretty validates and formats an already-serialized value with two-space indentation. json.object and json.array create empty containers. json.set, json.remove, and json.push return new JSON text values; they do not mutate the original string. json.get and the typed getters return the first occurrence when an input object contains duplicate property names. json.set replaces the first occurrence and collapses later copies of that same key into one property; unrelated properties, including their original order, are preserved. json.remove removes every occurrence of the selected key. Keys are escaped automatically, including quotes and control characters. json.escape validates UTF-8 and returns an empty owned string with json.last_error() set when its input is not valid UTF-8; successful JSON operations clear the previous diagnostic before processing, so successful escaping and empty-container creation do not leave a stale error; json.set rejects an invalid UTF-8 key as well. Values passed to json.set and json.push must already be valid JSON fragments (use json.escape for strings). Invalid fragments and non-object/non-array inputs return an empty owned string and set json.last_error(). Use json.escape when encoding a string value. This API is immutable: each builder returns a new owned_string, leaving its input unchanged. It is a raw-text builder, not a typed DOM; there are no object handles or in-place mutation.

Safety limits

  • Maximum input and generated output size: 16 MiB.
  • Maximum nesting depth: 128 containers (objects/arrays). Scalar values at the deepest level are valid; a 129th nested container is rejected.
  • Builder results are parsed again before being returned, so combining individually valid values cannot create a result deeper than the limit.
  • A generated output of exactly 16 MiB is permitted. This limit also applies to json.escape after accounting for quotes and escaped control characters. An output that would exceed 16 MiB terminates with a runtime error (exit status 70) rather than returning a truncated JSON document.
  • Invalid JSON is rejected, including malformed numbers, escapes, control characters, trailing data, and unpaired UTF-16 surrogate escapes.
  • Unicode \uXXXX escapes are decoded by json.get_string; surrogate pairs are combined into UTF-8.
  • Literal UTF-8 in JSON strings is validated; malformed, overlong, and surrogate UTF-8 sequences are rejected.
  • json.get_string reports U+0000 as unsupported because YLang’s current string representation is NUL-terminated.
  • The API is synchronous. It does not perform file or network I/O itself; combine it with io.read_file and http.*.

Formats and limitations

SDL2_mixer supports formats according to the codecs enabled in the installed build. Commonly available formats include WAV, Ogg Vorbis, FLAC, and MP3; do not assume every format is enabled on every platform.

This runtime manages one music track. voice.play_stream(http_stream) transfers ownership of the HTTP stream to the Voice runtime and reads it incrementally through SDL_RWops; the handle must not be used again by the caller. If stream setup fails, the runtime still closes the transferred handle. The custom source is forward-only and does not support seeking. Serialize playback and lifecycle calls on one owner thread. Stream callbacks may run on SDL_mixer’s audio thread, so they must be thread-safe and must not call Voice playback/lifecycle functions; ylvoice_last_error() is safe to call from other threads. Specific HTTP stream callback errors are preserved if decoding or playback startup fails, rather than being hidden by a generic SDL_mixer message. Error-state updates are synchronized across the playback and decoder paths; the C ylvoice_last_error() accessor returns a per-thread snapshot valid until its next call on that thread. voice.is_finished() reports natural end-of-track; polling either playback-state query releases the completed mixer object. Codec support for MP3 and other formats still depends on the installed SDL2_mixer build. It does not yet provide text-to-speech, audio recording, multiple simultaneous music streams, per-sound channels, playlists, or playback-rate changes.

The C backend is the supported backend for this optional runtime. The experimental NASM backend does not implement voice.*.

A slice shares its parent’s storage: changing a byte through either handle is visible through the other. Slices may be nested. A slice cannot be resized, cleared, or appended to; it can be read, modified, and saved. Freeing any buffer invalidates that buffer and all nested descendant slices, releasing their handle slots together. Shrinking a parent makes out-of-range slices temporarily inaccessible. You may still free a slice explicitly when it is no longer needed. The runtime releases any buffers not explicitly freed during normal program cleanup. Handles are process-local and must not be persisted.

Endian-aware integers

The API provides io.read_u16_le/be(path, offset), io.read_u32_le/be(path, offset), and io.read_u64_le/be(path, offset), plus matching io.write_u16_le/be(path, offset, value), io.write_u32_le/be(...), and io.write_u64_le/be(...) functions.

  • le means little-endian; be means big-endian.
  • 16-bit and 32-bit reads return nonnegative values in int.
  • 64-bit reads return the raw 64-bit pattern represented by the signed int type. Values with the high bit set therefore appear negative.
  • Scalar reads return -1 on failure; for 64-bit values, -1 can also be the valid all-bits-set pattern. Check io.binary_size when distinguishing that case matters.
  • Writes accept an int and write its low 16, 32, or 64 bits.

Streaming large files

Streaming avoids loading an entire file into memory. Handles are integer IDs managed by the runtime.

function main() -> int {
    let int input = io.stream_open_read("large.dat");
    if (input < 0) return 1;

    let byte chunk[] = [byte(0), byte(0), byte(0), byte(0)];
    let int count = io.stream_read(input, chunk);
    while (count > 0) {
        // Process chunk[0] through chunk[count - 1].
        count = io.stream_read(input, chunk);
    }

    if (!io.stream_close(input)) return 1;
    return 0;
}
  • io.stream_open_read(path) opens a file for reading.
  • io.stream_open_write(path) creates or truncates a file for writing.
  • io.stream_read(handle, buffer) returns the number of bytes read, zero at EOF, or -1 on error.
  • io.stream_write(handle, buffer) returns the number of bytes written, or -1 on error.
  • io.stream_close(handle) closes a handle. The runtime also closes any still-open streams during normal program cleanup.
  • At most 64 streams may be open simultaneously. Invalid or already-closed handles fail.

Complete example

function main() -> int {
    let string path = "header.bin";
    let byte data[] = [byte(0x59), byte(0x4c), byte(0x41), byte(0x4e)];

    if (io.write_bytes(path, 0, data) != 4) return 1;
    print(io.binary_size(path));
    print(io.read_u32_be(path, 0));
    return 0;
}

Limitations

  • Byte arrays are fixed-size. Use the dynamic io.buffer_* API when a growable byte buffer or a non-owning slice is required.
  • Streaming is synchronous and does not yet expose seek, flush, append, or async operations.
  • Runtime file offsets use portable C stdio seek operations and must fit the platform’s long range.
  • Binary I/O is experimental and currently supported by the C backend. The NASM backend reports a clear unsupported-type/API diagnostic.
  • The existing io.read_file and io.write_file functions remain text APIs.

std.tui — Terminal UI

YLang includes a small synchronous TUI runtime for interactive terminal programs. It provides raw key input, dimensions, cursor movement, screen clearing, ANSI output, and a portable sleep function.

The runtime restores terminal state on normal exit and, on POSIX, on SIGINT, SIGTERM, SIGHUP, and SIGQUIT before terminating. It does not yet provide mouse events, key-release events, Unicode grapheme editing, terminal resize events, or a full widget/layout system. Re-query dimensions during the event loop. The C backend is supported; the experimental NASM backend rejects TUI calls. POSIX raw-key behavior is covered by a pseudo-terminal integration test. Windows raw input still needs dedicated interactive CI coverage.

GUI and Game2D

The optional GUI runtime uses SDL2. The Game2D helper module is a small, experimental layer for learning and simple 2D prototypes—not a general-purpose game engine.

It provides helpers for window lifecycle, event polling, keyboard and mouse input, elapsed frame time, rectangle drawing, collision checks, and presentation. The repository includes a playable Dodge example. This chapter explains the setup and development workflow; the Game2D Library Reference and GUI API Contract define the exact API and its limitations.

Before you start

You need a working YLang compiler, a supported C toolchain, SDL2 development files, and `pkg-config`. Runtime testing also requires a graphical desktop session. The SDL2 runtime alone may not provide the headers and metadata needed to compile the example.

On Fedora, install the development dependencies with:

```sh sudo dnf install SDL2-devel pkgconf-pkg-config ```

On Debian or Ubuntu:

```sh sudo apt install libsdl2-dev pkg-config ```

On macOS with Homebrew:

```sh brew install sdl2 pkg-config ```

For Windows, follow the dedicated Windows Setup instructions; the native path has additional toolchain and packaging restrictions.

Build the example

From the repository root, run:

```sh make game2d-example ```

This builds the example as `build/dodge` on Linux and macOS, or `build/dodge.exe` on Windows. Run it from a graphical desktop session:

```sh ./build/dodge ```

On Windows, run `build/dodge.exe` from the appropriate MSYS2 environment.

If the build cannot find SDL2, check that its development files are installed and that `pkg-config` can locate them. If the program compiles but no window appears, confirm that you are running it in a graphical session rather than a headless terminal or CI environment.

What the frame loop does

A small real-time application typically repeats a few tasks:

  1. Poll input and window events so the application can respond to user actions.
  2. Update the program state, such as player position.
  3. Check collisions or other simple game rules.
  4. Draw the current frame.
  5. Present the frame and continue until the user closes the window.

Keep the update logic separate from drawing where practical. This makes the game easier to reason about and makes non-graphical logic easier to test.

Understand the limitations

Headless CI verifies type-checking, compilation, linking, and non-window helper behavior. It does not verify that a live window behaves correctly on every desktop, display server, or graphics driver. Test the game on a real graphical session before relying on it.

The library does not yet provide sprites, advanced animation, audio, a scene system, or a complete physics engine. Do not assume it is a replacement for a mature game engine. Check the API contract for supported functions and the exact behavior of window and event operations.

Troubleshooting

  • SDL2 headers or libraries are missing: install the development package for your platform.
  • `pkg-config` cannot find SDL2: check the package installation and environment paths.
  • The example builds but no window appears: run it from an interactive graphical desktop session.
  • A feature is missing: check the Game2D reference before assuming it exists.
  • The behavior differs across operating systems: record the platform, compiler version, and smallest example, then compare the documented support levels.

Practice

Build and run the Dodge example. Identify where it reads input, updates game state, checks collisions, and draws the frame. Make one small change, rebuild, and test it in a live graphical session. Keep the change within the API described by the Game2D reference.

Platform Support

YLang has different support levels on each platform. Installation instructions do not imply the same backend coverage everywhere. The default C-backend workflow depends on GCC or Clang, while optional libraries and experimental backends add their own requirements.

Use this chapter as an overview, then read the linked platform guide and test the features your project actually uses.

Linux

Linux is a primary development platform for the C backend and the experimental NASM x86-64 subset. GCC and Clang are supported C compiler choices. A compatible Linux x86-64 system can also install the optional YSPM package; see YSPM Linux Packages.

For ordinary command-line programs, a C toolchain and Make are the main requirements. GUI/Game2D needs SDL2 development files and `pkg-config`. The NASM backend is experimental and supports a narrower set of programs than the C backend.

macOS

macOS is tested with Clang and GNU Make. Install Apple’s command-line developer tools and use Homebrew for GNU Make and optional SDL2 dependencies. Use `gmake` rather than the system BSD `make` when following repository commands.

GUI/Game2D programs need SDL2 development files and `pkg-config`. Verify the native toolchain and run the project’s tests in the environment where you intend to build your application.

Windows

The initial native path targets 64-bit Windows with MinGW-w64 from the MSYS2 MINGW64 environment. CI tests compilation, a native executable, relative imports, standard input, and SDL2 build/link. MSVC is not supported by this first milestone, and full Windows feature parity is not claimed.

Read the Windows Setup guide for toolchain commands and current restrictions. A program that builds on Linux may depend on an unsupported feature or library on Windows, so validate the subset your project uses rather than assuming complete portability.

Backend coverage is separate from OS support

The C backend is the default and broad-coverage route. The NASM backend is experimental and limited to a subset of the language on supported Linux x86-64 systems. A platform having a working compiler does not mean that every backend is available there.

Similarly, a source file passing `check` does not guarantee that it can be built by every backend. Use `build` for the default C route and only use the experimental assembly commands after checking the Backend Roadmap.

A practical portability checklist

Before claiming that an application supports a platform:

  1. Build it with the supported toolchain on that platform.
  2. Run the relevant unit and regression tests.
  3. Verify native dependencies and linking.
  4. Test runtime behavior, including file paths, console input, and failure cases.
  5. If it uses GUI/Game2D, run it in a real graphical session.
  6. Record known unsupported features instead of describing the application as fully portable.

Report a platform issue

Include the operating system and architecture, compiler version, selected backend, exact build command, full diagnostic output, and a minimal source file that reproduces the problem. This information helps distinguish a language issue from a platform dependency or backend limitation.

YLang Core Language Specification — 2.0.0

This document defines the stable core language contract for YLang 2.0.0. Named imports, structs, enums, GUI/Game2D APIs, the NASM backend, native Windows support, and YSPM packaging are documented separately and remain experimental; their behavior is not covered by the stable-core compatibility guarantee. Syntax not listed here is not part of the stable core contract.

Explicit conversions

YLang does not implicitly convert values between types. Use explicit conversion functions:

  • to_float(integer) converts a signed 64-bit integer to a double-precision float.
  • to_int(float) truncates toward zero and terminates with a runtime error if the input is non-finite or outside the signed 64-bit range.
  • to_string(value) supports int, float, bool, char, and string. A string input is returned unchanged.
  • string.is_int(text) returns whether the entire string is a valid base-10 signed 64-bit integer.
  • string.parse_int(text) converts a valid integer string; invalid or out-of-range input produces a runtime error. Check with string.is_int first when parsing untrusted input.

1. Compilation model

YLang is a compiled language. ylang check parses and performs semantic checks. ylang build generates C and invokes GCC or Clang to produce a native executable. ylang emit-c writes C for inspection. There is no interpreter in this release.

2. Source form and statements

Statements end with ;, blocks use { and }, and comments use // through the end of a line or /* ... */ across lines. Block comments cannot be nested and must be closed. Keywords are lowercase and case-sensitive. Source files are text and embedded NUL bytes are rejected before lexing. Each source file passed to the CLI is compiled as one program. A program must define function main() -> int or function main() -> void, with no parameters.

3. Variables and constants

let int age;
let int score = 100;
let string name = "YLang";
let bool enabled = true;
let const int LIMIT = 100;
  • Mutable declaration: let type name; or let type name = expression;.
  • Constant declaration: let const type name = expression;. Constants must be initialized and cannot be reassigned.
  • A local variable must be assigned on every path before it is read. The checker rejects a read it cannot prove initialized.
  • Global variables without explicit initializers receive a type-appropriate zero/empty default. Explicit initialization is preferred.
  • A declaration can shadow a name in an outer block, but duplicate names within one scope are errors.
  • Assignment is a statement, not a general nested expression.

4. Types

No implicit numeric conversions are performed. Arithmetic operands must have compatible matching types. % is available only for int. Conditions must have type bool. Strings support equality and lexicographic ordering comparisons. String values are immutable.

User-defined enums (experimental)

Unit enums are supported as named, distinct types:

enum Direction { North, East, South, West }

function is_east(Direction direction) -> bool {
    return direction == Direction.East;
}

function main() -> int {
    let Direction facing = Direction.North;
    if (is_east(Direction.East)) { print("east"); }
    if (facing == Direction.North) { print("north"); }
    return 0;
}

Declare an enum before using its type. Refer to variants with EnumName.Variant. Values of different enum types cannot be mixed, and a variant can be passed to or returned from a function with the same enum type. Variants currently have no payloads. A statement match (value) { EnumName.Variant -> { ... } } must contain exactly one arm for every variant; missing and duplicate arms are errors. For this milestone, the matched expression must not contain calls or assignments. Enum formatting with print, importing enum types across module boundaries, payload variants, and explicit numeric discriminants are not implemented yet. The C backend and the experimental NASM backend represent these unit variants as integer values while semantic analysis preserves their distinct YLang types.

5. Literals and strings

let float ratio = 1.25;
let bool ready = true;
let char initial = 'Y';
let string message = "Hello
";
let string greeting = f"Hello {message}";

char is one byte, not a Unicode scalar. Integer literals support decimal notation and hexadecimal notation such as 0xFF; floating-point literals support decimal notation and scientific notation such as 1e3 or 2.5e-4. A string literal must be terminated. F-strings begin with f" and interpolate expressions inside {}. Supported interpolations include variables and operators. Function calls and assignments are not allowed inside interpolation expressions; compute the value in a preceding statement. Quoted string and character literals decode Character literals must decode to exactly one byte and may contain zero. String literals and f-string text reject zero bytes (\0or\x00) because YLang strings are NUL-terminated; use the byte-buffer API for binary data. F-strings apply the other supported escapes to literal text. Literal braces can also be escaped with doubled braces ({{and}}`).

6. Output

print(expression, ...) writes values separated by one space and appends a newline:

print("answer:", 42);
print(f"Count: {n}");

Supported printable values are int, float, bool, char, and string. print is a statement in this release.

7. Expressions and operators

  • Unary: -, not
  • Arithmetic: +, -, *, /, %
  • Comparison: ==, !=, <, <=, >, >=
  • Boolean: and, or
  • Assignment: = and += as statements; postfix ++ increments a mutable numeric variable by one
  • Grouping: (expression)
  • Calls: name(argument, ...)

Operator precedence is conventional: unary operators, multiplication/division/modulo, addition/subtraction, comparisons/equality, and, then or. Parentheses may be used to make grouping explicit. Evaluations with observable side effects are sequenced from left to right: function-call arguments, eager binary operands, struct initializer fields, and array initializer elements. For assignment, the target location is evaluated before the right-hand side. Boolean and and or short-circuit from left to right.

Signed integer overflow, integer division/modulo by zero, and floating-point division by zero are handled by generated runtime helpers and terminate the program with a runtime-error message and status 70. This does not mean every possible C-level issue is guarded or that the language is memory-safe.

Loops

Three loop forms are supported:

loop() {
    // Repeat until break.
    break;
}

while (count < limit) {
    count += 1; or count++;
}

for (let int i = 0; i < limit; i = i + 1) {
    print(i);
}
  • loop() is an unconditional loop.
  • while (condition) repeats while a boolean condition is true.
  • for (initializer; condition; increment) uses C-style clauses. The initializer may be a let declaration or expression; condition and increment may be omitted.
  • break; exits the innermost loop and continue; starts its next iteration.
  • A for initializer declaration is scoped to the loop and its body.

Fixed-size arrays

YLang supports fixed-size arrays with an explicit element type and an initializer. The length is inferred from the initializer. Arrays may be local or global, must contain at least one element, and all elements must have the same type.

let int scores[] = [10, 20, 30];

function main() -> int {
    scores[1] = 42;
    print(scores[0], scores[1], scores[2]);
    return 0;
}
  • Indexing starts at zero.
  • Array indices must be int; every access performs a runtime bounds check and exits with status 70 on an invalid index.
  • Element assignment is supported, such as scores[1] = 42;.
  • Whole-array assignment, returning arrays, nested arrays, and const arrays are not supported yet. Array parameters use type name[]; the generated native ABI passes a pointer and a separate length value.
  • Arrays must be initialized at declaration; their size cannot change at runtime.

Standard string and input library

YLang includes byte-oriented string helpers and a line reader for simple command-line programs:

let string name = io.read_line();
let string greeting = string.concat("Hello, ", name);
print(greeting);
print(string.length(name));
print(string.contains(name, "lang"));
print(string.starts_with(name, "Y"));
print(string.ends_with(name, "n"));
  • string.length(value) returns the number of bytes, not Unicode characters.
  • string.contains(value, needle), string.starts_with(value, prefix), and string.ends_with(value, suffix) return bool.
  • string.concat(left, right) returns a new string.
  • string.replace(value, needle, replacement) returns a new string with every non-overlapping occurrence of needle replaced. An empty needle leaves the original string unchanged.
  • string.upper(value) and string.lower(value) return case-converted copies using the C locale’s byte-oriented character mapping; they are not Unicode-aware.
  • Strings support lexicographic ordering with <, <=, >, and >=, using bytewise C-string ordering. Equality remains case-sensitive.
  • The generated runtime tracks allocated strings until process exit, so repeated concatenation or case conversion in a long-running loop can increase memory use.
  • io.read_line() reads one line from standard input and removes its trailing newline. At end-of-file it returns an empty string.
  • io.read_file(path) reads an entire UTF-8/ASCII-compatible text file into a string. A file-open/read failure or embedded NUL byte terminates the program with a runtime error; binary files are not supported by the string API.
  • io.write_file(path, content) overwrites or creates a text file and returns true on success or false if it cannot open/write the file. It does not create missing parent directories.
  • File paths are interpreted relative to the process working directory. File I/O is synchronous and currently has no structured error/exception type.
  • path.exists(path) returns whether a path can be inspected with stat; it may return true for files, directories, or other filesystem objects.
  • path.basename(path) returns the final path component, and path.extension(path) returns the suffix after the final dot (without the dot); a leading dot alone is not treated as an extension. These helpers use POSIX path separators.
  • image.open(path) launches the platform default opener (xdg-open on Linux, open on macOS) without invoking a shell and returns whether the launcher exits successfully. It requires a desktop session and a registered handler; it opens the file in an external application and does not decode or draw the image in a YLang window.

Terminal input and output

The C runtime exposes synchronous command-line helpers through terminal.*. terminal.read_line(prompt) returns an owned_string; terminal.read_int(prompt), terminal.read_float(prompt), and terminal.read_bool(prompt) parse one line and terminate with a runtime error on invalid input. Boolean input accepts true/false, yes/no, and 1/0. terminal.write(text) and terminal.write_line(text) return a boolean write status and flush stdout. terminal.clear() emits ANSI clear-screen sequences, while terminal.is_interactive() checks whether stdin is attached to a terminal. EOF in line input returns an empty string. Raw key events and password input are not supported. See std.terminal.

Experimental owned strings

The C backend has an experimental owned_string type. Unlike legacy string, an owned_string local owns its tracked heap allocation and is released automatically when its scope ends. This feature is not part of the stable 2.0.0 core compatibility contract and does not provide full Rust-style borrowing or lifetime checking.

let string text = "YLang";
let owned_string owner = string.own(text); // clones text into owned storage
let owned_string next = owned_string.concat(owner, "!");
let owned_string transferred = move(next); // next is unavailable until reinitialized
print(owner, transferred);

Use string.own(value) to clone borrowed text into owned storage. owned_string.concat, owned_string.replace, owned_string.upper, owned_string.lower, io.read_line_owned(), and io.read_file_owned(path) produce owned strings. Use move(name) to transfer one owner into another local, an owned-string function parameter, or an owned return value. A function that returns an owned value should return move(name) for a local binding. Implicit copying of an owned binding is rejected; use string.own(value) when a separate owned copy is required.

The compiler emits releases on normal scope exit and before return, break, and continue. Reassigning an owned variable releases its previous value. For allocation diagnostics, run the resulting program with YLANG_MEMORY_STATS=1; if all owned values have been released and the program created no other retained legacy strings, live tracked allocations and bytes should be zero at process exit.

The experimental borrowed_string type can be used for function parameters that read text without taking ownership:

function report(borrowed_string text) -> int {
    print(text);
    print(string.length(text));
    return 0;
}

function main() -> int {
    let owned_string message = string.own("hello");
    report(message); // message remains owned by main
    return 0;
}

A borrowed_string parameter is read-only. The type is rejected for local/global variables, struct fields, array parameters, and function return values. It does not free the passed value; the caller must keep the owner alive for the duration of the call. Passing an unbound owned_string temporary to a borrowed parameter is rejected. This is a limited immutable call-parameter view, not full lifetime inference or a general borrow checker.

Current limits: owned strings require the C backend. Global owned strings, arrays of owned strings, and owned-string struct fields are rejected until cleanup for those storage forms exists. Mutable borrows (&mut T), lifetime annotations, escaping borrows, and general alias checking are not implemented. Legacy string remains a borrowed C-string representation, and allocations produced by legacy string helpers may live until process exit. Do not treat this experimental feature as a security boundary or a claim of complete Rust-level memory safety.

Path and desktop integration

let string file = io.read_line();

The path namespace exposes exists, basename, and extension. These APIs currently target the POSIX systems supported by YLang.

Standard math library

YLang provides a built-in math namespace for common floating-point operations. These calls are checked by the compiler and emitted as native C math-library calls.

let float root = math.sqrt(81.0);
let float power = math.pow(2.0, 8.0);
let float angle = math.sin(0.0);
let float bounded = math.clamp(12.0, 0.0, 10.0);

Available functions (all arguments must be float, and all return float):

  • Unary: sqrt, sin, cos, tan, asin, acos, atan, sinh, cosh, tanh, exp, log, log10, floor, ceil, round, abs.
  • Binary: pow, atan2, min, max, hypot.
  • Three arguments: clamp(value, low, high); a lower bound greater than the upper bound triggers a runtime error.

YLang does not implicitly convert integers to floats, so use float literals such as 9.0. Domain errors and non-finite results follow the platform C math library behavior.

8. Conditions and loops

if (age >= 18) {
    print("Adult");
} else if (age >= 13) {
    print("Teenager");
} else {
    print("Child");
}

loop() {
    if (done) {
        break;
    }
    continue;
}

Conditions must be boolean. loop() repeats indefinitely until break executes. while repeats while its condition is true, and for supports initializer, condition, and increment clauses. continue skips to the next iteration. break and continue are only valid inside a loop.

9. Functions

function add(int left, int right) -> int {
    return left + right;
}

function main() -> int {
    print(add(20, 22));
    return 0;
}

Parameter and return types are explicit. Function overloading is not supported. A non-void function must return a value on supported control-flow paths. main has no parameters and returns int or void.

10. Modules and imports

A source file can import named functions or global variables from another .yl file:

from "./system_data.yl" import system_data, system_prefix;

function main() -> int {
    print(system_data(), system_prefix);
    return 0;
}

Import paths are resolved relative to the file containing the import, not the process working directory. Imports are transitive: an imported module may import names from another module. Every name used from another module must be imported explicitly. Functions and globals declared in a module are visible inside that module, but do not become visible to importers unless their names are imported. Different modules may define private helpers with the same name.

The compiler rejects unknown imported names, conflicting or repeated imports, imports of the program entry point, missing module files, and circular imports. The root source file must define main(); an imported module cannot define it. Imports are currently supported by the default C backend. The experimental NASM backend rejects multi-file imports explicitly until module-aware assembly lowering is implemented.

11. Diagnostics and tooling

check reports parse and semantic/type diagnostics without invoking a native compiler. Diagnostics include an error code, file/line/column, source excerpt, caret, and a hint when one is available. build does not produce a successful executable if YLang diagnostics contain errors.

fix input.yl -o output.yl currently implements one high-confidence source transformation: changing a pritn(...) call typo to print(...) when no function named pritn is declared. It requires an output path and does not intentionally modify comment/string text. It is not a general repair engine. Always run check after applying a fix.

JSON documents

The native json.* namespace parses and validates JSON without a third-party dependency. It supports nested objects and arrays, JSON escapes, and UTF-16 surrogate-pair decoding. Input is limited to 16 MiB and nesting to 128 levels.

  • json.parse(text) validates and retains a JSON document as owned_string.
  • json.valid(text) checks syntax and returns bool.
  • json.get(document, key) returns a property as raw JSON; typed accessors include json.get_string, json.get_int, json.get_float, and json.get_bool.
  • json.has(document, key) checks for an object property; json.array_length and json.at inspect arrays.
  • json.at uses zero-based indices; a negative or out-of-range index returns an empty string and sets json.last_error().
  • json.stringify(raw) validates and copies an already-serialized JSON value. json.pretty(raw) formats one with two-space indentation.
  • json.escape(text) encodes a YLang string as a JSON string literal; json.last_error() returns the latest diagnostic.

This remains a raw-document API, not a mutable JSON DOM: it does not construct typed objects or arrays from YLang values. The unreleased 2.3 development line adds immutable raw-text builders (json.object, json.array, json.set, json.remove, and json.push); they accept validated JSON fragments and return new JSON strings, not a dynamic value tree. See the JSON guide for the current API and release boundary.

Binary file I/O (experimental)

The optional byte scalar type is an unsigned 8-bit integer. byte(value) checks that an int is in the range 0..255 and returns a byte; an out-of-range conversion terminates with a runtime error. Fixed arrays can be declared as let byte data[] = [byte(0), byte(255)];; byte-array parameters also work with the block and stream APIs.

The binary file API includes io.binary_size, io.read_u8, io.write_u8, io.read_bytes, io.write_bytes, io.read_binary_hex, and io.write_binary_hex. Buffer functions accept a named byte array and return a byte count, or -1 on error. Hex helpers remain limited to 16 MiB per call.

Dynamic byte buffers are available through opaque integer handles: io.buffer_new, io.buffer_slice, io.buffer_length, io.buffer_capacity, io.buffer_get, io.buffer_set, io.buffer_push, io.buffer_resize, io.buffer_clear, io.buffer_free, io.buffer_load, and io.buffer_save. Buffers grow automatically, are limited to 256 MiB each, and at most 64 may be live. Resizing to a larger length zero-fills new bytes. Invalid handles or indices return documented sentinel values/false. Slices are non-owning views that share parent storage and cannot be resized. Freeing a buffer invalidates that buffer and every nested descendant slice. Buffers not explicitly freed are released during normal runtime cleanup.

Endian-aware scalar helpers are available for unsigned 16-, 32-, and 64-bit values in both little- and big-endian forms: io.read_u16_le/be, io.read_u32_le/be, io.read_u64_le/be and matching io.write_u16_le/be, io.write_u32_le/be, io.write_u64_le/be. 64-bit reads return the raw bit pattern through signed int, so values with the high bit set appear negative; -1 is also the failure sentinel.

Streaming uses io.stream_open_read(path), io.stream_open_write(path), io.stream_read(handle, byte_array), io.stream_write(handle, byte_array), and io.stream_close(handle). Stream reads return zero at EOF and -1 on error. The runtime supports up to 64 simultaneous streams and closes remaining handles during normal cleanup. Streaming is synchronous and currently has no seek or async operation.

All these facilities are experimental, synchronous, and supported by the C backend only. They do not yet provide memory-mapped files or asynchronous streams. Text file APIs remain separate.

12. Unsupported features and implementation limits

The following are not supported by the current language subset: classes, methods on structs, inheritance, payload enums, generic Option<T>/Result<T, E>, exception syntax (try/catch), generics, raw pointers/references, returning arrays, nested/const arrays, and a dedicated LLVM/native backend. Typed structs and enums are implemented as experimental extensions described in the struct reference and the enum reference; they are not part of the stable-core compatibility guarantee. class, try, and catch may be tokenized as reserved words but are not valid executable constructs.

The compiler generates C, so native code inherits ordinary process privileges and is not sandboxed. Some formatted string values are stored until process exit; creating many such values in a long-running loop can increase memory consumption. The language does not define ownership/borrowing or a garbage collector in this release. Do not assume Rust-like memory-safety guarantees.

YLang 2.0 Module System — Proposal

Status: named local-file imports are implemented on the development branch; aliases and qualified module imports remain proposals. Treat this implementation as experimental until its CI matrix passes and the limitations below are resolved.

The compiler supports selective imports of top-level functions and globals using a local source path. It intentionally does not define a package registry or binary module ABI.

1. Current behavior and remaining limitations

A source file may import named declarations from another .yl file:

from "./string_tools.yl" import system_data;

The resolver loads transitive dependencies, resolves paths relative to the importing file, rejects cycles, and keeps each module’s declarations and imports separate during semantic analysis. Only explicitly imported names are visible to the importer; helper declarations remain private to their source module. Generated C function names are module-qualified to avoid collisions. Imported modules may not define main(), and the root program must provide the entry point.

Current limitations: import aliases and import "module.yl" as module are not implemented; there is no package manifest or registry. Quoted paths and dotted filenames are supported, and YLANG_PATH searches colon-separated library directories after the importing file’s directory. The NASM backend can now lower imported modules for its existing supported subset; unsupported imported features still produce explicit backend diagnostics, and NASM remains experimental.

2. Proposed syntax

Selective imports

Keep the existing spelling for compatibility:

from "math.yl" import clamp
from "text.yl" import trim, split

Optional empty parentheses after imported names may remain accepted during a deprecation period, but new examples should omit them because an import names a symbol, not a call.

Aliases

Use an explicit as clause:

from "text.yl" import trim as trim_text

function main() -> int {
    let string cleaned = trim_text("  hello  ");
    print(cleaned);
    return 0;
}

An alias changes only the local name. It must not rename the original declaration in its defining module. Duplicate local names in the same scope must produce a compiler diagnostic even if they originate from different modules.

Module-qualified imports

Allow importing a module under a local namespace name:

import "math.yl" as math

function main() -> int {
    print(math.clamp(12, 0, 10));
    return 0;
}

The exact punctuation can change during parser review, but the semantic rule should not: a qualified reference resolves only to an exported declaration in that specific module. It must not fall back to searching all flattened source files.

3. Name visibility rules

  1. A source file is one module, identified internally by its canonical resolved path for local imports.
  2. A module declaration belongs to that module only; it does not automatically become visible to the importing module.
  3. A selective import creates a local binding only for each named symbol, or its explicit alias.
  4. A qualified import creates one local module binding; declarations are accessed through that binding.
  5. A symbol not imported or declared in the current module is an unknown-name error, even if another reachable module happens to define it.
  6. A module may refer to its own declarations without importing itself.
  7. Until an explicit visibility modifier exists, declarations intended for import are exported by default. A future private modifier may narrow visibility, but must not be silently inferred from filename or declaration order.
  8. Duplicate local bindings are errors. Two modules may define the same function name without conflict when those functions are referenced through distinct module bindings.
  9. Cyclic imports remain rejected in the first stable milestone. Supporting cycles later would require a separate declaration/signature collection pass and clear initialization rules.

4. Resolution and compilation architecture

Do not implement namespaces by rewriting every source file into a single string and then relying on the global symbol table.

Use a staged architecture:

  1. Resolve: parse import directives and normalize paths relative to the importing file. Enforce current limits on module count, nesting, and total source size.
  2. Load once: keep one module record per canonical path and report path errors against the import site.
  3. Declare: collect top-level function and type signatures per module before analyzing bodies. This permits forward references within a module and gives a basis for future cycle support.
  4. Bind imports: build a module-local symbol table mapping local names to a defining module and declaration.
  5. Analyze: resolve every identifier using local declarations and explicit imports only. Report both the use site and, where useful, the conflicting binding.
  6. Lower/codegen: pass a resolved symbol identity (module ID plus declaration ID) to the backend. The C backend may mangle internal names to avoid linker collisions; this is an implementation detail, not language-visible syntax.
  7. Diagnostics: retain source spans for each original file so all errors point to the correct path and line.

The C backend can continue to compile the generated C as one translation unit initially, provided symbol identity and visibility have already been resolved correctly. Separate object files and a stable module ABI are later work, not prerequisites for correct source-level namespaces.

5. Diagnostics

Reserve stable diagnostics for module-specific failures. Proposed names are illustrative until added to the compiler’s diagnostic registry:

  • malformed import syntax or invalid alias;
  • file not found, unreadable file, or unsupported path;
  • imported symbol does not exist in the specified module;
  • name is not visible in the current module;
  • duplicate local binding caused by two imports or an import/local declaration collision;
  • cyclic import, including the full cycle chain where practical.

Diagnostics should name the importing file and line. When a symbol exists but is not imported, suggest the explicit import only when the candidate is unambiguous.

6. Required acceptance tests

The module system should not be marked stable until all of these pass in the ordinary test suite:

  • Existing single-file programs behave identically.
  • Selective imports work with one and multiple symbols.
  • Two import directives can import different symbols from the same file without duplicate definitions.
  • Quoted paths with spaces and paths relative to the importer work.
  • Nested dependencies work independent of declaration order.
  • Cycles fail with a stable diagnostic.
  • A function present in a reachable module but not explicitly imported cannot be called.
  • An imported symbol can be renamed with as; the original name is not implicitly added to the local scope.
  • Two modules can define functions with the same name and calls to each qualified name reach the correct implementation.
  • Duplicate aliases and alias-vs-local-name collisions fail before backend compilation.
  • A symbol imported from module A is not automatically re-exported through module B unless re-export syntax is explicitly designed.
  • Compile-fail tests check diagnostic codes and source locations.
  • GCC, Clang, Windows, and sanitizers continue to pass where supported.

7. Migration plan

  1. Add resolver and semantic tests that describe the intended visibility rules.
  2. Introduce per-module declaration tables while retaining the existing syntax.
  3. Enforce selective-import visibility and reject accidental access to unimported declarations.
  4. Add selective-import aliases.
  5. Add qualified module imports and allow duplicate function names across modules.
  6. Update the language guide and examples only after parser, semantic analysis, and all supported backends agree.

Each step should be a separate reviewable change. Do not add package manifests, registry downloads, inheritance, or raw pointers as part of this module-system work.

8. Non-goals

This proposal does not promise a package manager, dependency versioning, binary compatibility across compiler releases, dynamic linking, cyclic module initialization, or a Rust-equivalent safety guarantee. Local-file imports should remain deterministic and should not execute arbitrary build scripts.

Structs (experimental)

YLang’s current struct milestone supports named fields with explicit types, positional construction, field reads, passing structs to functions, returning structs, and assignment between values of the same struct type.

struct Point {
    int x;
    int y;
}

function shift(Point p, int dx) -> Point {
    return Point(p.x + dx, p.y);
}

function main() -> int {
    let Point p = shift(Point(2, 7), 3);
    print(p.x, ",", p.y);
    return 0;
}

Current limits

  • Declare a struct before using it; its fields must have valid non-void types.
  • Construct with positional arguments in declaration order: Point(2, 7).
  • Field reads and assignments are supported for named mutable struct variables, including chained access through nested structs, for example p.x = 10; or hero.pos.x = 10;. The final field type is checked, and the root variable must be mutable.
  • No recursive by-value fields, methods, inheritance, generic structs, field defaults, or named constructor arguments.
  • The C backend supports structs; NASM parity has not been established.
  • This is experimental until the implementation PR and its CI matrix are reviewed and merged.

See YLang 2.0 design.

Enums and exhaustive matching (experimental)

YLang’s current enum milestone supports unit enums: named alternatives with no attached payload. Every enum declaration creates a distinct type, even when another enum has the same variants.

enum Direction { North, East, South, West }

function is_east(Direction direction) -> bool {
    return direction == Direction.East;
}

function main() -> int {
    let Direction facing = Direction.North;
    match (facing) {
        Direction.North -> { print("north"); }
        Direction.East -> { print("east"); }
        Direction.South -> { print("south"); }
        Direction.West -> { print("west"); }
    }
    return 0;
}

Rules

  • Declare the enum before using its type or variants.
  • Write variants as EnumName.Variant.
  • Enum values can be stored in variables, passed to functions, returned, and compared with == and !=.
  • Assigning values from different enum types is a type error.
  • match (value) must include every variant exactly once. Missing variants and duplicate arms are errors.
  • Each arm uses Variant -> statement; a block is recommended for clarity.
  • In this milestone, match values must be simple side-effect-free expressions; store a value in a variable before matching it.
  • Enums are represented as integer tags in the C backend. Do not depend on the numeric tag values.
  • Payload variants, generic enums, matching bindings, and NASM parity beyond the tested unit-enum subset are not promised as stable.

The syntax and semantics are experimental until the feature PR is reviewed and merged. See YLang 2.0 design for the remaining value-type roadmap.

YLang GUI API Contract (Proposal)

Status: implemented on main as an optional SDL2-backed binding surface. The API below describes the current first milestone; native GUI builds require SDL2 development files, while check and ordinary non-GUI builds do not.

This document defines a deliberately small first binding milestone. The contract must be agreed before changing the parser, semantic checker, C generator, and native build driver together.

Goals

  • Make a small graphical window usable from ordinary YLang source.
  • Preserve the current default build: programs without gui.* calls must not need SDL2.
  • Keep check independent of SDL2 installation; dependency discovery belongs to native build.
  • Validate argument count and types before code generation.
  • Keep the API portable across the project’s supported Linux and macOS targets.
  • Make unsupported calls fail with YLang diagnostics rather than producing broken C.

Proposed first API

The first milestone intentionally supports one active window per process. It does not expose raw pointers or arbitrary C interop.

gui.init()boolInitialize the GUI runtime; false means initialization failed.
gui.create_window(title, width, height)boolCreate one window; title is string, dimensions are positive int values.
gui.poll()boolProcess pending events; false means the window was closed or polling failed.
gui.key_down(key)boolCheck a named key after polling; supports SDL scancode names such as Left, Space, and Escape.

Example target syntax

This example shows the intended use of the API and is included in the implementation work.

function main() -> int {
    if (not gui.init()) {
        print(gui.last_error());
        return 1;
    }

    if (not gui.create_window("YLang GUI", 800, 500)) {
        print(gui.last_error());
        gui.shutdown();
        return 1;
    }

    loop() {
        if (not gui.poll()) { break; }
        if (not gui.clear(24, 28, 38)) { break; }
        if (not gui.draw_rect(80, 80, 240, 120, 22, 160, 180)) { break; }
        if (not gui.present()) { break; }
    }

    gui.close();
    gui.shutdown();
    return 0;
}

The example is available as examples/gui.yl. The regression suite checks its types and generated C; an SDL2 runtime smoke test runs when the development package is available.

Compiler and build requirements

  1. Parser: accept gui as a recognized standard-library namespace using the same qualified-call representation as existing namespaces.
  2. Semantic analysis: define an explicit signature table for every supported call; check arity and each argument’s type; assign the documented return type. Unknown gui.* names must produce a stable diagnostic.
  3. C generation: emit calls to a narrow adapter layer. Do not pass arbitrary user-selected C symbols through to generated code.
  4. Native build driver: detect whether the checked program uses GUI calls. Only then discover SDL2 compiler/linker flags and link the optional runtime. Use argument-vector process execution, not a shell command string.
  5. Portability: account for the repository-relative runtime source and headers, and report a clear build error if SDL2 development files are missing. The ordinary non-GUI build must continue working without SDL2.
  6. Experimental NASM backend: reject GUI calls with a clear unsupported-feature diagnostic; do not silently generate invalid assembly.
  7. Documentation: clearly label this as an optional SDL2 feature and distinguish compile-time checking from dependency-required native building.

Acceptance tests

  • check accepts a well-typed GUI program even on a machine without SDL2 installed.
  • check rejects incorrect arity, wrong argument types, unknown GUI names, and invalid types with source-located diagnostics.
  • A regular non-GUI program builds and runs with no SDL2 dependency.
  • A GUI program builds on Linux and macOS when SDL2 development files are installed.
  • A GUI build with missing SDL2 reports the required package/tooling and exits nonzero.
  • Runtime initialization/window-creation failure is reportable through gui.last_error().
  • The existing C GUI example and all compiler regression tests remain passing.
  • The NASM backend rejects GUI programs before assembly generation.

Deliberate non-goals for the first milestone

No widget toolkit, text input, images, audio, a reusable game-loop abstraction, multiple-window handles, custom event objects, arbitrary FFI, or full Pygame-like game framework. Those should build on the first API only after its ownership, error, and lifecycle behavior is tested.

YLang Compiler Architecture

YLang 2.0.0 uses a conventional multi-stage compiler pipeline. The stable core compiles through generated C and GCC/Clang; named imports, structs, enums, GUI/Game2D, and the NASM backend are explicitly experimental extensions.

  1. Lexer (src/lexer.c) — turns source text into positioned tokens.
  2. Parser (src/parser.c) — builds the program representation and calls shared diagnostics when syntax is invalid.
  3. Frontend utilities — src/arena.c owns arena allocation and arena-backed vectors; src/strbuf.c owns generated-text buffers; src/diagnostics.c formats source-located errors and warnings.
  4. Semantic analysis (src/sema.c) — resolves names, validates initialization and constant assignment, and checks types.
  5. Module loader (src/module.c) — recursively loads imported files, detects cycles, resolves named imports, and merges module ASTs while retaining per-module visibility.
  6. C code generator (src/codegen.c) — writes C for the checked program, including runtime helpers for supported checked arithmetic operations.
  7. Driver (src/driver.c) — orchestrates module loading and checking, writes generated C, and invokes GCC or Clang without going through a shell.
  8. CLI (src/main.c) — parses user commands and their options.

The internal compiler model is declared in src/internal.h; the public-facing compiler and token declarations are in include/ylang/.

Experimental NASM backend (Linux x86-64)

The optional emit-asm command writes NASM syntax for a deliberately limited subset of YLang. Unlike the default C backend, the generated program uses the Linux x86-64 system-call ABI for output and process exit, so a generated program can be assembled with NASM and linked directly with ld without GCC/Clang or a C runtime:

./build/ylang emit-asm tests/asm-basic.yl -o build/asm-basic.asm
nasm -f elf64 build/asm-basic.asm -o build/asm-basic.o
ld -o build/asm-basic build/asm-basic.o
./build/asm-basic

For the same steps in one command, use build-asm:

./build/ylang build-asm tests/asm-basic.yl -o build/asm-basic
./build/asm-basic

The initial subset supports scalar int, bool, char, and string values, local variables, up to six scalar function parameters, user-defined function calls, integer arithmetic and comparisons, if/else, loops, break, continue, return, and print. Integer overflow and invalid integer division terminate the program with status 70.

The experimental backend currently rejects global declarations, arrays, floats, f-strings, string comparisons, and/or, standard-library or conversion calls, and multi-file imports. The standard build command continues to use the established C backend. The separate build-asm command runs NASM and ld for supported programs; emit-asm writes the assembly source for inspection. The experimental backend is Linux x86-64 specific and is not supported on macOS or other architectures.

Diagnostic policy

Compiler errors are intended to be stable, user-facing output. Changes should preserve useful codes where practical and include regression tests for source locations and hints. A check failure must not be reported as a native build failure. Code generation is only entered after parsing and semantic analysis report no errors.

Native backend

The v1.0 backend generates C17 and invokes the selected native compiler (gcc by default or clang when selected). Linux builds use GNU linker RELRO/NOW hardening and _FORTIFY_SOURCE; macOS builds omit GNU/Linux-specific flags and use the platform linker. Generated programs are ordinary native executables, not sandboxed. For native builds, generated C is placed in a private temporary directory and removed after the native compiler exits. This avoids clobbering a project file and avoids collisions between concurrent build invocations. emit-c writes to the requested path, or build/ylang-generated.c if no output path is given.

Scope

This architecture documents the current implementation, not a promise of features outside docs/language-spec.md. Arrays, pointers/references, classes, exception syntax, and a finalized memory model are intentionally outside the original 1.0.0 feature set. Named imports are supported by the default C backend; the NASM backend remains a limited experimental subset.

Backend strategy and roadmap

Current state

  • YLang’s compiler front end and type checker are written in C17.
  • The default ylang build backend emits C, then invokes GCC or Clang to produce an executable. This is the broadly supported path for the beta.
  • The experimental NASM backend emits Linux x86-64 assembly for a restricted subset and links with NASM plus ld. It does not support every feature accepted by the C backend.
  • Programs requiring the optional SDL2 runtime need the documented native dependencies; the NASM backend rejects GUI calls explicitly.

This means YLang programs do not yet have a complete, general-purpose native backend independent of GCC/Clang. The NASM subset is not a drop-in replacement for the C backend.

Design principles

  1. One front end. Parsing, name resolution, type checking, and diagnostics stay shared. Do not implement language semantics separately inside each backend.
  2. Typed intermediate representation first. Before expanding the NASM subset or starting another backend, introduce a documented, backend-neutral representation that preserves resolved types, control flow, imports, and source locations.
  3. Declare capabilities. Each backend must have a tested capability matrix. Unsupported language constructs must cause explicit diagnostics before emission; never silently emit a different behavior or fall back without telling the user.
  4. C remains the reference path for broad coverage. The C backend stays the default until an alternative covers the required language subset and passes the same behavior tests.
  5. Differential testing is mandatory. For every construct supported by more than one backend, compile the same source with each backend and compare stdout, stderr/runtime-error classification, and exit status. Keep small regression fixtures for arithmetic, control flow, enum matching, and imports.
  6. Fuzz the shared front end. Keep lexer/parser unit tests and run the libFuzzer harness under AddressSanitizer and UndefinedBehaviorSanitizer in CI where toolchain support is available.

Proposed milestones

B0 — 2.0 beta

  • Keep C/GCC/Clang as the default supported build path.
  • Keep NASM explicitly experimental and limited to its documented Linux x86-64 subset.
  • Run differential parity tests on the common subset; report skips on unsupported platforms instead of implying parity was tested.

B1 — Backend-neutral typed IR

  • Specify expression, statement, type, control-flow, module/import, and source-location representations.
  • Add IR invariants and tests independent of any target backend.
  • Move code generation gradually behind a backend interface without duplicating semantic checks.

B2 — Native backend proof of concept

Evaluate two options with a small, measurable prototype:

  • LLVM IR/object output, for mature optimization and target support, while explicitly accounting for LLVM toolchain size and deployment costs.
  • Direct machine-code or assembly generation, if a small dependency footprint is more important, with target-specific code isolated from the language semantics.

The decision should be based on executable correctness, portability, debug information, compile time, binary size, maintenance cost, and cross-backend test coverage—not on a target date or a single benchmark.

B3 — Expand only behind parity gates

  • Extend a backend only when the IR and tests express the feature fully.
  • Require parity fixtures for the feature’s supported subset and compile-fail diagnostics for unsupported combinations.
  • Keep runtime/standard-library dependencies explicit and versioned.

B4 — Reassess the GCC/Clang requirement

Only advertise a general independent backend after it can build and run the supported language suite on every claimed target from a clean checkout. Building YLang’s compiler itself may still require a C toolchain unless a separate bootstrap path is implemented.

Out of scope

This is a roadmap, not a promise that LLVM, a direct machine-code backend, Windows support, or a self-hosting compiler will ship in the 2.0 beta. Do not delay the beta for those future milestones, but do not imply that the current NASM subset already removes the C compiler requirement for general YLang programs.

YLang Debugger

Status: experimental 2.2 development feature. The CLI can create a debug build and launch the system-native debugger. This is not yet a complete YLang Debug Adapter Protocol implementation, and it does not claim full debugger support on Windows or across both code-generation backends.

Reproducible Performance Measurements

Status: development tooling. Numbers are machine-specific and should not be treated as release guarantees.

Run the native benchmark

Build YLang first, then run the same workload on the same host and toolchain before and after a change:

python3 benchmarks/bench-native.py benchmarks/native-loop.yl \
  --cc gcc --runs 30 --warmup 3 \
  --expected-file benchmarks/expected-native-loop.txt

Use --cc clang for the Clang path. The optional --compiler /path/to/ylang chooses the compiler executable. Add --keep-dir build/benchmark-artifacts to preserve the final generated executable for inspection.

The report shows the YLang version, host platform and architecture, reported CPU model, selected native C compiler version, requested and effective optimization level, core C build flags, compile-time median and P95, execution-time median and P95, and executable byte size. The expected-output check ensures that the benchmark is still measuring a program with known behavior rather than a broken output path.

What is measured

  • Compile time includes the YLang invocation, semantic checking, C generation, and native compiler/linker run.
  • Run time includes starting the executable and its exit; stdout/stderr capture and process creation are part of the measurement. This is not a pure instruction-cycle benchmark.
  • Binary size is the size of the final executable produced by the last measured build.
  • Warm-up iterations are not included in the reported samples. P95 is the nearest-rank 95th percentile.

The CI smoke test verifies that the harness executes and reports its metrics; it intentionally does not enforce a universal speed target. Do not compare measurements from different machines, native compiler versions, optimization settings, power modes, or workloads as if they were a controlled experiment.

Suggested comparison record

For performance-sensitive changes, keep the commit SHA, YLang version, operating system/architecture, native compiler version, YLANG_OPT_LEVEL, run count, warm-up count, median, P95, binary size, and expected program output together. Re-run several times if a result is close to the noise floor. Prefer stable improvements across repeated measurements over a single faster number.

std.terminal — Terminal input and output

YLang provides a small synchronous terminal API through the built-in terminal.* namespace. It is intended for command-line applications and does not require an external package.

Example

function main() -> int {
    let owned_string name = terminal.read_line("Name: ");
    terminal.write_line(f"Hello, {name}");

    let int age = terminal.read_int("Age: ");
    let float score = terminal.read_float("Score: ");
    let bool confirmed = terminal.read_bool("Continue? (yes/no): ");

    print(age, score, confirmed);
    return 0;
}

Behavior and limits

  • Input is line-oriented and synchronous. read_line removes the line ending and supports arbitrarily long lines subject to available memory.
  • EOF in read_line returns an empty string, matching the existing io.read_line behavior.
  • Invalid numeric or boolean input terminates the program with a descriptive runtime error (status 70). Integer overflow and non-finite floats are rejected.
  • Prompts are written to stdout and flushed before waiting for input.
  • is_interactive checks stdin; redirected input and pipes return false.
  • clear emits ANSI escape sequences. It does not attempt terminal capability detection.
  • The terminal.* API is line-oriented. For raw key events, terminal dimensions, cursor movement, ANSI output, and interactive screen control, use the separate std.tui runtime.
  • The C backend is supported. The experimental NASM backend does not implement standard-library terminal calls.

Security Model and Safe Defaults

YLang is a compiled toolchain, not a sandbox. A YLang executable runs with the privileges of the user who starts it. The compiler does not isolate file access, processes, network access, or imported native code.

Compiler resource limits

The compiler bounds several input-driven resources to keep malformed or unexpectedly large projects from consuming unbounded memory or call-stack depth:

  • At most 100 diagnostics are printed for one compilation; source-line excerpts are limited to 160 bytes and non-printable/non-ASCII bytes are escaped in diagnostic output. When a diagnostic token belongs to a source buffer, its line excerpt is located from the token offset rather than rescanning from the start of the file.
  • A program may load at most 1,024 source modules.
  • The root source and all imported source files together are limited to 64 MiB. The root file is size-checked before allocating its contents; imported files are size-checked before each allocation. Embedded NUL bytes are rejected in both root and imported source files rather than being treated as end-of-file.
  • Module import recursion is limited to 256 levels.
  • Parser statement nesting is limited to 256 levels, and code generation has a defensive 512-level statement-depth guard.
  • JSON input and generated JSON output are each limited to 16 MiB; JSON nesting is limited to 128 levels.

The compiler reports the module limits with E1027, E1028, and E1029, and statement-depth violations with E1018/E1019. These limits are compiler safeguards, not a sandbox; native programs still run with the user’s permissions.

HTTP/HTTPS client

The experimental C-backend client uses libcurl and applies these defaults:

  • Only http:// and https:// URLs are accepted. TLS certificate and hostname verification remain enabled; there is no insecure verification bypass.
  • Connection attempts time out after 5 seconds and the entire request after 15 seconds.
  • Response bodies are capped at 8 MiB, and request/response header text is bounded to 16 KiB.
  • Automatic redirects are limited to five and allowed only for HTTP/HTTPS. The built-in JSON Content-Type header is permitted through redirects, but if the request includes any other header, a 3xx response is returned directly rather than forwarding arbitrary headers such as X-API-Key to a new target.
  • HTTP status codes such as 401, 404, and 500 are response statuses, not transport errors. Check http.status() and http.last_error() separately.
  • At most 32 HTTP task handles may be in flight. http_task values are process-local, single-consumption handles; cancellation does not undo a request already received by the server.
  • HTTP streaming uses a separate pull-based API with at most 16 active streams and a fixed 64 KiB response buffer. It has a 5-second connection timeout but intentionally no whole-transfer timeout, so long-lived streams are possible. A program must close streams it no longer needs; process shutdown also releases them.
  • Buffered synchronous and task-based HTTP response APIs return text strings. If a response body contains NUL, they return an empty string and expose an error directing the caller to binary-safe streaming.
  • YLang strings are NUL-terminated. Escaped NUL bytes in string/f-string literals, NUL bytes from line input, and NUL bytes produced by string formatting are rejected instead of being silently truncated; binary data belongs in byte buffers.
  • http.stream_read() is text-oriented and rejects chunks containing embedded NUL bytes through http.stream_error(). Use http.stream_read_buffer() with a root io.buffer for binary data, and free that buffer when finished.

These safeguards reduce common accidental leaks and resource exhaustion, but they do not make a caller-supplied URL safe in every deployment. In server-side applications, validate URLs against an application-specific hostname/IP allow-list and consider access to loopback, private, link-local, and metadata addresses before making a request.

API keys and environment variables

Use env.get("SERVICE_API_KEY") to read a credential supplied by the parent process. Missing variables return an empty string. The helper does not invoke a shell and does not grant additional permissions.

Do not commit real API keys, print them in diagnostic output, or include them in generated source files. Use the credential mechanism supported by the host or CI environment, restrict keys to the minimum permissions required, and rotate leaked credentials.

Native execution and debugging

  • ylang build, ylang debug, and the native executable run code on the host with the invoking user’s normal permissions.
  • Debugging is not a privilege boundary or sandbox. GDB/LLDB can inspect process state according to the user’s operating-system permissions.
  • The experimental debugger is implemented for the C backend on Linux (GDB) and macOS (LLDB). Windows interactive debugging and the NASM source-debugging path are not implemented.
  • Generated C and compiler diagnostics are developer tools, not a guarantee that arbitrary programs are memory-safe. YLang does not claim Rust-level memory safety; continue running regression tests, sanitizers, and fuzzing on supported environments.

For a security report, include the affected commit, OS/toolchain, exact compiler command, minimal reproducible source, and whether the issue reproduces with a non-privileged account. Do not post live credentials or private user data in an issue.

YLang Debugger Design

Status: design proposal for the YLang 2.2 roadmap. No debugger command or VS Code debug configuration should be advertised as implemented until this specification is accepted and the implementation passes its tests.

Goal

Let a developer debug a .yl file from VS Code or the command line, seeing YLang source locations and meaningful variable names rather than generated C internals.

Initial scope

The first implementation should target the established C backend. Support for the NASM backend is out of scope until it can emit and verify appropriate debug information.

The first milestone should aim to provide:

  • Build and launch a YLang program with debug symbols.
  • Set source-line breakpoints, continue, step over, step into, and step out.
  • Show the current YLang source location and call stack.
  • Inspect supported local scalar variables.
  • Display clear errors when the compiler, native debugger, symbols, or source mapping are unavailable.

Inspection of arrays, structs, owned values, optimized code, and generated runtime internals should be added only when each representation can be exposed reliably.

Compiler and source mapping

  1. Add an explicit debug build mode; do not silently change the normal optimized build.
  2. Compile generated C with debug symbols and debugging-friendly optimization settings.
  3. Preserve a mapping between YLang source files/lines and generated C. A prototype should evaluate generated-C #line directives and any additional source-map metadata needed for expressions or locals.
  4. Preserve source file identity for relative imports and files outside the current working directory.
  5. Keep temporary generated sources and binaries in a predictable, documented location, and make cleanup behavior explicit.
  6. Do not rely on C variable names alone as the permanent YLang debugger interface.

A source-level breakpoint must land on a valid executable statement. If a line contains only a declaration, comment, or compound construct with no instruction location, the adapter should explain or resolve the breakpoint rather than claiming that it was bound exactly.

Debug-engine choice

Before settling the public interface, implement a small proof of concept and compare:

  • Reuse the VS Code C/C++ debugger: generate appropriate launch configuration and source mapping, with a clearly declared dependency on the C/C++ extension.
  • Provide a YLang debug adapter: implement the Debug Adapter Protocol and communicate with a supported native debugger such as GDB/LLDB.

Choose based on reliable YLang source stepping, local-variable inspection, cross-platform behavior, installation complexity, and maintenance cost. Do not commit the extension’s public debugger type until the prototype shows that generated-C details can be hidden adequately. Never invoke a shell command assembled from user-controlled source paths or program arguments.

VS Code user experience

The desired flow is:

  1. Open a YLang workspace and select a YLang debug configuration.
  2. Press F5; the extension checks required tools and builds a debug executable if necessary.
  3. Set breakpoints in the .yl editor and use the usual Run and Debug controls.
  4. See the call stack, supported locals, and console output in the normal VS Code panes.
  5. Receive actionable setup diagnostics if GCC/Clang or the native debugging engine is missing.

The extension must not automatically install or execute an untrusted debugger or compiler. Tool installation remains an explicit user action.

Runtime safety and correctness

  • Debugging is not a security sandbox; the program still runs with the user’s normal permissions.
  • Use argument-vector process APIs and validate executable paths.
  • Do not change runtime semantics to make a variable appear inspectable.
  • Keep ordinary builds independent from debugger dependencies.
  • Preserve program arguments, environment variables, working directory, stdin/stdout, exit status, and termination behavior.
  • Separate compiler errors from debugger startup errors and target-program failures.

Acceptance tests

Use small YLang programs with known output and state to verify:

  • Breakpoint binding to a specific source line.
  • Continue, step-over, step-into, and step-out behavior.
  • Correct source display for a function in an imported module.
  • Call stack names and lines for nested YLang functions.
  • Values of supported local integers, floats, booleans, and strings at a breakpoint.
  • Handling of optimized-out/unavailable values without fabricated output.
  • Missing debugger, invalid source, build failure, early exit, and user-requested termination.
  • Paths with spaces and non-default working directories.
  • Existing release and sanitizer tests remain passing.

Platform support

Document debugger-engine requirements per platform. The initial support claim must match what CI and local integration tests actually exercise; a successful Linux prototype is not evidence of Windows or macOS parity.

Option and Result design for YLang 2.0

Status: design proposal only. This document does not claim that Option or Result are implemented.

Goals

  • Represent absence and recoverable failure without magic sentinel values.
  • Keep YLang’s explicit typing rule: no implicit conversion between int, float, string, or other types.
  • Make failure paths visible to the type checker.
  • Keep the stable 1.1.x language behavior unchanged until the feature is implemented and tested.

Recommended first implementation: tagged values, not generics

The current type system does not yet provide general type parameters. Do not pretend that Option<T> or Result<T, E> work until generic types, payload layout, and code generation are implemented.

For an incremental milestone, introduce compiler-internal tagged values with concrete payload types, then generalize only after the type representation can express type parameters safely. The surface syntax should be finalized before code changes.

Conceptual semantics:

  • Option<T>: either Some(value) or None.
  • Result<T, E>: either Ok(value) or Err(error).
  • Matching must be exhaustive, like the existing unit-enum match checks.
  • Accessing a payload is legal only after the checker proves which variant is active.
  • No implicit conversion is performed for payloads or errors.

Proposed user-facing examples (illustrative, not currently compilable)

// Illustrative syntax only; do not use as a working example yet.
let Option<int> maybe_port = Some(8080);

match maybe_port {
    Some(port) => { print(port); }
    None => { print("no port"); }
}

// Illustrative syntax only; do not use as a working example yet.
let Result<int, string> parsed = parse_port("8080");

match parsed {
    Ok(port) => { print(port); }
    Err(message) => { print(message); }
}

Implementation sequence

  1. Type representation: define type identity for payload-bearing variants and ensure incompatible payload types cannot be mixed.
  2. Parser and AST: parse generic type arguments and variant payload patterns without changing existing enum parsing.
  3. Semantic analysis: validate constructors, payload types, duplicate arms, exhaustive matching, and payload binding scope.
  4. C backend: emit a tagged representation with explicit payload storage and safe access only in matching arms.
  5. Assembly backend: keep the feature disabled for NASM until parity tests exist; do not silently route it through an unverified fallback.
  6. Tests: cover Some/None, Ok/Err, nested payload types, wrong payloads, duplicate/missing arms, and use of payloads outside a matching arm.
  7. Docs and release gate: label the feature experimental until Linux GCC, Linux Clang, macOS Clang, sanitizers, and backend parity tests pass.

Non-goals for the first milestone

  • General user-defined generics.
  • Implicit conversions or exception-like hidden control flow.
  • Assuming all errors are strings.
  • Claiming full assembly-backend support before executable tests pass.

Acceptance criteria

  • Stable 1.1.x examples remain unchanged.
  • Every invalid payload construction is rejected with a targeted diagnostic.
  • Exhaustiveness and payload scope are checked at compile time.
  • The generated program has deterministic behavior for every variant.
  • CI proves the same observable behavior on supported C compilers.

YLang 2.0 — Language and Ecosystem Design

Status: proposal, not an implementation guarantee.

This document defines the order in which YLang 2.0 should grow. The guiding rule is to land small, testable language changes rather than introducing syntax that the semantic analyzer and backends cannot enforce.

Goals

  • Keep YLang readable and approachable while making invalid states harder to express.
  • Make compiler diagnostics and behavior consistent across GCC/Clang C builds and the experimental NASM backend.
  • Define type, initialization, ownership, and error-handling semantics before exposing pointers or object-oriented features.
  • Ship reproducible compiler releases, a package format, documentation, and a minimal official website.

Non-goals for the first 2.0 milestone

  • Claiming Rust-level memory safety before ownership and lifetime rules are implemented and tested.
  • Supporting every feature in every backend at once. Unsupported features must fail with a diagnostic rather than silently miscompile.
  • A public package registry before dependency integrity, version resolution, and lockfile behavior are specified.
  • Class inheritance, reflection, async/await, or JIT compilation in the first milestone.

Backend strategy

The C backend remains the default for broad language coverage; it emits C and invokes GCC/Clang. The NASM backend is experimental, restricted to Linux x86-64, and must reject unsupported constructs. YLang does not yet have a complete general-purpose native backend independent of GCC/Clang. The plan is to define a shared typed intermediate representation, keep backend capabilities explicit, and require differential output/exit-status tests for the subset supported by multiple backends. A future proof of concept may evaluate LLVM IR or direct machine-code generation; neither is promised for the 2.0 beta. See BACKEND-ROADMAP.md.

Milestone 0 — Compiler correctness

Before new type syntax:

  1. Make definite-initialization analysis consistent for assignments, compound assignments, increment/decrement, branches, and loops.
  2. Add regression tests for each diagnostic and valid programs near those boundaries.
  3. Test the C backend with GCC and Clang; run AddressSanitizer and UndefinedBehaviorSanitizer in CI where supported.
  4. Keep the NASM backend explicitly experimental until its supported-language matrix and parity tests are clear.
  5. Run generated executables and compare output and exit status; a successful build alone does not prove runtime correctness.

Acceptance criteria:

  • Each known bug has a regression test.
  • CI reports the compiler, target OS/architecture, and sanitizer result.
  • No feature is marked stable only because it parses.

Milestone 1 — Value types: struct and enum

Start with value types, not heap-allocated classes.

Current experimental subset (available on the development branch; not yet a stable 2.0 guarantee):

struct Point {
    float x;
    float y;
}

function distance_squared(Point point) -> float {
    return point.x * point.x + point.y * point.y;
}

function main() -> int {
    let Point point = Point(3.0, 4.0);
    print(distance_squared(point));
    return 0;
}

Unit enums and exhaustive match statements are also implemented experimentally. See STRUCTS.md and ENUMS.md for the tested subset and explicit limitations.

Required rules:

  • A struct declaration has a stable, compile-time-known field layout.
  • Every field must be initialized before an instance can be read.
  • Field reads and writes are type-checked; unknown fields produce a dedicated diagnostic.
  • Duplicate fields and duplicate type declarations are rejected.
  • Copy/value semantics must be documented before structs can be passed, returned, or nested.
  • Recursive by-value fields are rejected unless a later indirection type makes their size finite.
  • Structs must not be accepted by the NASM backend until layout and field operations are implemented there.

Then add enums with exhaustive matching. Do not add pattern matching syntax until exhaustiveness and unreachable-case rules are specified.

Milestone 2 — Explicit absence and errors

Not implemented yet. Introduce Option<T> and Result<T, E> only after the compiler has a reliable generic/type representation. The current enum implementation has unit variants only and cannot carry payload values.

Illustrative future syntax (not currently guaranteed to compile):

let result: Result<int, ParseError> = string.parse_int(text);
match result {
    Ok(value) => print(value),
    Err(error) => print(error.message),
}

Rules:

  • Missing values must not be represented by undocumented magic integers or null strings.
  • Option<T> must force callers to handle the absent case, using matching or a documented unwrap API.
  • Result<T, E> must distinguish success from failure and preserve the error value.
  • Exhaustiveness checks must reject missing cases.
  • Generic instantiation and diagnostics need tests for nested types and invalid type arguments.

Milestone 3 — Memory model before pointers

Do not add raw pointer syntax before deciding who owns allocations and how long references remain valid.

Proposed order:

  1. Define value versus owned heap types.
  2. Define deterministic cleanup semantics and behavior on early return.
  3. Add immutable and mutable references with explicit aliasing rules.
  4. Reject references that can outlive their referent.
  5. Add raw pointers only for low-level interoperability, behind an explicit unsafe boundary.
  6. Provide checked allocation and null handling at the safe API boundary.

Safety requirements:

  • No read of uninitialized storage.
  • No safe use-after-free or dangling reference.
  • No safe dereference of null.
  • No unchecked pointer arithmetic in safe code.
  • Bounds checks remain in place for safe indexing.
  • FFI and unsafe operations must be visibly marked and documented.

A runtime tracker that frees allocations at process exit is not a substitute for an ownership model. A borrow checker is a substantial feature and should be implemented incrementally with compile-fail tests.

Milestone 4 — Object-oriented features (deferred; not part of 2.0)

OOP is intentionally deferred. Do not add methods, classes, inheritance, or receiver semantics to the 2.0 release work; focus on Windows portability, YSPM system-package integration, and the playable minimal Game2D sample.

Add methods only after structs and field access are stable.

Preferred initial model:

  • Methods associated with a named type.
  • Explicit receiver semantics (self by value or by reference).
  • Encapsulation through access modifiers with documented defaults.
  • Interfaces/traits for behavior shared across types.
  • Composition preferred over inheritance initially.

Class/reference semantics and inheritance are separate design decisions. Do not silently make all structs heap objects or add inheritance without defining identity, initialization order, dispatch, destruction, and cycle behavior.

Milestone 5 — Generics and standard library

Generic types and functions must specify type inference, constraints, monomorphization/code generation, and error messages. Start with a small set of constraints rather than unrestricted templates.

Standard-library priorities:

  • Option/Result and string parsing.
  • File and path APIs with explicit error handling.
  • Collections with clear ownership and bounds behavior.

YLang 2.0.0 — Stable Release

YLang 2.0.0 establishes the stable compatibility contract for the documented core language and the default C-backend compiler workflow. This release keeps the language’s explicit typing, source-located diagnostics, and inspectable C-generation pipeline as the supported foundation.

Important compatibility boundary: not every component introduced during the 2.0 development cycle is stable. The experimental subsystems listed below may change in future releases and are explicitly outside the stable-core compatibility guarantee.

Stable core

  • Explicit declarations, constants, fixed-size homogeneous arrays, scalar types, functions, and structured control flow.
  • Explicit conversions and type checking, initialization checks, clear diagnostics, and safe rejection of unsupported syntax.
  • The default ylang build path: validate .yl source, generate C, and invoke GCC or Clang for a native executable.
  • Core strings, formatted strings, standard input, text file I/O, math helpers, path utilities, and checked runtime behavior documented by the core specification.
  • The check, build, emit-c, and fix command-line workflows, with the limitations of each command documented in the README.

The stable language contract is defined in the core language specification. Where this release notes page and the reference differ, the specification and the explicit experimental labels in the relevant feature guide define the supported behavior.

Experimental extensions

These features are available for evaluation, but are not covered by the stable-core compatibility promise:

  • Named imports and multi-file compilation. No package registry, dependency solver, import aliases, or qualified module namespaces are promised.
  • Structs and enums. Several advanced forms remain unsupported; consult the struct reference and the enum reference.
  • GUI and Game2D. The optional SDL2-backed APIs are not a mature general-purpose game engine. Interactive window behavior requires a graphical session.

YLang Memory Model — RFC

Status: partial implementation in the experimental C backend. The compiler has an explicit owned_string type with move-only binding transfers and generated cleanup at ordinary block exits, function returns, loop breaks, and loop continues. A restricted immutable borrowed_string function-parameter view is also implemented. General &T / &mut T borrow syntax, conflicting-borrow checks, and full Rust-like lifetime analysis are still unimplemented.

Goals

  • Keep the default language free of a tracing garbage collector and of periodic GC pauses.
  • Free owned heap allocations deterministically when their owner leaves its lifetime.
  • Reject use-after-move, dangling borrows, and conflicting mutable borrows at compile time.
  • Preserve checked integer arithmetic and array bounds checks unless the compiler proves a check unnecessary.
  • Avoid reference counting on ordinary owned values; no cycle collector should be required for the core model.
  • Keep the stable 2.0.x language behavior unchanged while the feature is developed behind explicit tests and a release gate.

Non-goals for the first milestone

  • A tracing garbage collector.
  • Shared mutable ownership, weak references, or cyclic owning references.
  • A global allocator replacement or a promise that every program will be faster than C.
  • Silently changing existing string, array, or struct behavior before a migration plan exists.
  • Treating C code generation as a memory-safety sandbox.

Proposed ownership categories

The compiler must classify values rather than relying on the C type alone:

  1. Scalar values: int, float, bool, char, and unit-enum values. These are copied by value.
  2. Owned values: initially dynamic strings, and later owning structs/containers. Every owned value has exactly one owner at a time. Assignment or pass-by-value moves ownership; the old binding becomes unavailable.
  3. Shared immutable borrows: &T. Multiple immutable borrows may coexist while the owner remains alive.
  4. Exclusive mutable borrows: &mut T. Only one exclusive mutable borrow may be active, and no immutable borrow may overlap it.
  5. Non-owning views: any future slice/string-view type must carry a checked lifetime and may never outlive its backing owner.

The precise surface syntax and which standard-library operations borrow or consume a value must be finalized before implementation. The notation above is a design direction, not currently compilable syntax.

Lifetime and cleanup rules

  • A local owner is destroyed at the end of its lexical scope.
  • Returning an owned value transfers ownership to the caller.
  • Returning a borrow is allowed only when the type system can prove that the referent outlives the returned borrow; the first implementation may forbid borrowed returns.
  • Passing an owned value to an ordinary by-value parameter transfers ownership. A borrow parameter does not consume its argument.
  • Every control-flow exit (return, break, continue, and normal block exit) must run exactly the destructors for owners whose scopes are exited.
  • Cleanup must be emitted on all paths. The generated C must not rely on non-portable compiler extensions for destructors.
  • A resource is released exactly once. Use-after-move and double-release must be rejected or made impossible by generated code.
  • If ownership cannot be determined, compilation must fail with an actionable diagnostic rather than guessing.

Current experimental progress

Implemented: experimental owned_string and explicit moves

The C backend and semantic checker support:

let owned_string source = string.own("YLang");
let owned_string joined = owned_string.concat(source, "!");
let owned_string destination = move(joined);
print(source, destination);

owned_string is a separate experimental type. string.own(text) clones text into tracked heap storage; owned_string.concat/replace/upper/lower and io.read_line_owned / io.read_file_owned return owned values. The source of move(name) becomes unavailable (diagnostic E2110) until reinitialized. Implicit copies of owned bindings are rejected (E2115); returning an owned local requires return move(name) (E2116). Moves are merged conservatively across branches, loops, and exhaustive match arms. Self-move assignment is rejected (E2114).

Generated C keeps owned slots initialized to null and emits yl_release calls on ordinary scope exit and before return, break, or continue. Transferred values are nulled at the source, so cleanup is safe to run on every path. Assigning a new owned value releases the previous value. The runtime release helper only frees pointers registered by YLang’s allocation tracker, so string literals and other untracked pointers are not freed accidentally.

The existing string type remains a legacy C-string representation; runtime-created legacy strings can still be retained until process exit. owned_string is supported only by the C backend for now. Global owned strings, arrays of owned strings, and owned-string struct fields are rejected (E2118) until global, array-element, and field cleanup are implemented. User functions that accept owned_string take ownership of that argument; call them with move(name) or a fresh owned expression.

The separate experimental borrowed_string type is permitted only for function parameters. Such parameters are immutable, are passed as non-owning pointers, and cannot be stored in a local/global variable, a struct field, or a return type. They may be forwarded only to other borrowed_string parameters or used immediately by non-retaining string helpers. An owned_string temporary is rejected when passed into a borrowed parameter because the temporary would have no named owner to keep it alive for the call. This provides a narrow immutable parameter view, not a general lifetime checker: the language still has no &mut T, no returned borrows, and no general alias analysis.

The first runtime instrumentation commit adds an opt-in diagnostic:

YLANG_MEMORY_STATS=1 ./your-program

When the generated program exits normally, it writes a line to standard error with the number of currently tracked payload allocations and their requested payload bytes. The counters saturate rather than wrapping. This is diagnostic instrumentation only: it does not reclaim memory earlier, the byte count excludes tracker-node and allocator overhead, and it is not a measurement of resident RAM. Programs using the existing tracker still retain those allocations until yl_cleanup().

The test suite includes an opt-in fixture and checks that enabling the diagnostic does not alter normal program output. Ownership, borrowing, and scope-based release are not implemented by this instrumentation.

First implementation slice

Implement this in small, reviewable steps:

  1. Flow-sensitive ownership facts (in progress): current checks model explicit moves and merge them conservatively, but complex control-flow should continue to gain regression cases.
  2. Borrow checker: design explicit immutable and mutable borrow syntax, then reject dangling/conflicting borrows, borrowed moves, and returned local references.
  3. Signature and inter-module ownership contracts: make ownership transfer vs borrow behavior explicit for all functions and imported signatures.
  4. Cleanup coverage: expand and verify cleanup for all control-flow edges, then add arrays, structs, globals, and nested owners only when their drop semantics are defined.
  5. Runtime verification: test allocations/frees under AddressSanitizer and LeakSanitizer where available, plus repeated-request stress tests.
  6. Expand only after parity: add arrays and structs with owned fields once strings pass the full test matrix.

Required compile-pass tests

  • Moving an owned value makes its source binding unavailable.
  • An immutable borrow can be read multiple times while its owner is alive.
  • Mutation through &mut T is permitted only with exclusive access.
  • Returning an owned value keeps it valid in the caller.
  • Inner-scope cleanup does not invalidate values that were moved out.
  • All valid examples have identical observable behavior under GCC and Clang.

Required compile-fail tests

  • Use after move.
  • Borrow after owner destruction / returning a local borrow.
  • Two overlapping mutable borrows.
  • Mutable and immutable borrows that overlap incompatibly.
  • Double move from one binding.
  • Moving a value while it is borrowed.
  • Invalid use of a moved value on any control-flow branch.

Performance and memory acceptance criteria

  • No regression in stable 2.0.x behavior before the feature is explicitly enabled.
  • For a long-running test that repeatedly creates and discards owned buffers, live owned bytes must return to a bounded baseline after each request/scope completes.
  • Measure peak RSS, total allocated bytes, total freed bytes, and request throughput; RSS alone is insufficient because allocators may retain freed pages.
  • Compare equivalent workloads with equivalent overflow/bounds semantics and the same native compiler flags.
  • No performance claim based on one microbenchmark. Use repeated runs, warmups, multiple workload families, and report medians and variance.
  • Keep checked arithmetic and bounds checks unless proven redundant by analysis. Any check-elision optimization needs tests that cover both provably safe and potentially overflowing inputs.

Open design decisions

  • Whether current string remains a copyable borrowed view and a new String type owns bytes, or whether a future major release changes string to an owned, move-only value.
  • Borrow syntax and inference rules.
  • Whether array slices are introduced with the first owned type or later.
  • How imported functions expose ownership/borrow information in module signatures.
  • How debug diagnostics explain ownership conflicts without producing cascaded errors.

  • string.own(text) creates an owned copy.

  • Owned-string helpers include concat, replace, upper, and lower; owned input helpers include io.read_line_owned and io.read_file_owned.
  • Generated cleanup is emitted for owned locals at normal scope exit and before return, break, and continue.
  • borrowed_string is available as a restricted immutable function-parameter view.

Important limitations

This milestone is not a complete Rust-like ownership or borrowing system.

  • These ownership features currently require the C backend.
  • Owned globals, arrays of owned strings, and owned-string struct fields remain unsupported.
  • borrowed_string is restricted to immutable parameters; borrowed returns and local/global/field storage are not supported.
  • General &T and &mut T syntax, full lifetime analysis, and general alias/conflicting-borrow analysis are not implemented.
  • The existing string type retains its legacy allocation behavior and is not automatically made memory-safe by this change.
  • YLang does not claim Rust-level memory safety or provide a security sandbox.

Review the actual workflow results for the exact commit; a successful earlier PR run is not a substitute for testing this release candidate.

Upgrade guidance

Existing programs using string do not need to migrate to owned_string. Treat the new ownership APIs as experimental and opt in only where the documented restrictions are satisfied. Do not assume that adding owned_string makes all allocations in a program automatically reclaimed.

YLang 2.2.0 — Stable Release

YLang 2.2.0 expands the developer toolchain with experimental HTTP/API requests, asynchronous HTTP tasks, environment-variable access, and source-aware native debugging. The documented core language and default C-backend workflow remain the compatibility foundation.

Compatibility boundary: the HTTP client, HTTP-task async API, debugger integration, named imports, structs/enums, GUI/Game2D, NASM backend, native Windows path, and YSPM packaging have explicit experimental limitations. This release does not claim Rust-level memory safety, a security sandbox, general-purpose async functions, a dynamic typed JSON value tree, a complete VS Code Debug Adapter Protocol implementation, or Windows interactive debugging.

Highlights

  • HTTP and API requests: synchronous helpers and http.request(method, url, body, headers) for GET, POST, PUT, PATCH, DELETE, and HEAD through optional libcurl support.
  • Asynchronous HTTP tasks: http.request_async(...) returns an http_task; await task consumes it and returns the response body; http.cancel(task) requests cancellation. The libcurl multi interface lets multiple transfers progress while tasks are awaited.
  • Response and error inspection: http.status(), http.response_headers(), and http.last_error() expose the latest response status, headers, and transport/configuration error.
  • JSON text helpers: the standard library includes JSON parsing, validation, typed getters, escaping, and formatting. It represents documents and extracted values as owned JSON strings rather than a dynamic typed value tree. Immutable object/array builders are part of the 2.3 development work.
  • Environment access: env.get(name) reads process environment variables without invoking a shell, allowing programs to obtain credentials without hard-coding them.
  • Security defaults: request-method and header validation, a 16 KiB header limit, an 8 MiB response-body limit, connect and overall timeouts, HTTPS certificate/hostname verification, and restricted redirect behavior for requests carrying custom headers.
  • Source-aware debugger: ylang debug builds with -O0 and debug symbols, then launches GDB on Linux or LLDB on macOS. Generated C source mappings let supported breakpoints refer to original .yl locations.
  • Developer tooling: updated VS Code and Neovim syntax support for http and env, a terminal-based VS Code debug command, and repeatable compile/runtime/binary-size benchmark tooling.
  • Documentation and website: refreshed homepage, online book, reference pages, and candidate-acceptance tooling.

Known limitations

  • Async/await applies only to HTTP task handles. General async functions, a background scheduler, and GUI/event-loop integration are not implemented.
  • HTTP response bodies are strings. JSON helpers operate on raw JSON text; they are not a typed DOM, and callers must validate provider-specific fields and malformed responses.
  • Programs that use http.* require libcurl development files and pkg-config when linking. Ordinary programs do not require libcurl.
  • HTTP method names are case-sensitive and must be uppercase. HTTP status codes such as 404 are not transport failures; callers must inspect http.status().
  • Debugging is an initial CLI workflow, not a complete Debug Adapter Protocol implementation. Local-variable names and some scopes may reflect generated C. Interactive debugging is supported on Linux with GDB and macOS with LLDB; Windows and the NASM backend do not have a source-level debugger contract.
  • Experimental extensions are not covered by the stable-core compatibility guarantee and do not provide a security sandbox or complete Rust-like memory safety.
