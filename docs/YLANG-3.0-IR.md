# YLang 3.0 Typed IR — Verifier Contract

Status: standalone typed SSA verifier plus an expanding scalar AST lowering slice. The lowerer supports nested conditionals, scalar SSA merges, `while`, `for`, `loop()`, `break`, `continue`, short-circuit `and` / `or`, direct imported user-function calls, and an initial finite-f64 subset alongside i64 and bool. Function signatures and direct calls support scalar int/float/bool values and int/float/bool/void returns. General language lowering and production backend integration remain incomplete; LLVM, NASM, and the production C build path do not consume this IR yet.

## Design constraints

- The IR is independent of C syntax and target instruction sets. Direct user-function calls carry a readable callee name, a module-qualified callee symbol, typed argument values, and the checked scalar parameter signature. A function lowered from a module receives a symbol built from its canonical module path plus `::` and its source function name, while unowned AST unit-test functions fall back to their source name. The function verifier checks argument value types and SSA dominance, while `yir_verify_module` resolves the qualified symbol to one unique function and compares its complete scalar signature. This allows same-named functions in different imported modules without ambiguous calls; duplicate symbols are rejected.
- Every produced value has an explicit type and a function-wide unique SSA identifier.
- The first block is the function entry.
- Every block ends in exactly one explicit terminator.
- Lowered instructions retain source line and column locations when available.
- Values may cross blocks only when their definition dominates the use.
- Non-entry blocks may declare typed parameters. Branch edges pass one value per target parameter, in order.
- Typed scalar int and bool function parameters are modeled as entry SSA values. Entry block parameters, other parameter types, external calls, memory operations, and ownership metadata are not modeled yet.

## Current types and operations

Types: `void`, `bool`, `i64`, `f64`, and opaque `ptr`.

Operations currently implemented: `const.i64`, finite `const.f64`, `const.bool`, `add.i64`, `sub.i64`, `mul.i64`, `div.i64`, `mod.i64`, `neg.i64`, `add.f64`, `sub.f64`, `mul.f64`, `div.f64`, `neg.f64`, `eq.i64`, `ne.i64`, `lt.i64`, `le.i64`, `gt.i64`, `ge.i64`, `eq.f64`, `ne.f64`, `lt.f64`, `le.f64`, `gt.f64`, `ge.f64`, `not.bool`, direct typed `call`, `br`, `cond_br`, and `return`.

Branch and conditional-branch terminators may carry typed edge arguments. Those arguments initialize the target block's parameters, providing the SSA merge mechanism for control-flow joins.

## Verifier guarantees

The verifier checks:

- Non-empty functions and blocks, unique block IDs, and valid type tags.
- Exactly one final terminator in each block.
- Existing branch destinations and reachable blocks from the entry.
- Function-wide unique SSA identifiers, including function and block parameters.
- Operand type agreement and definition-before-use within a block.
- Cross-block use only when the defining block dominates the use.
- Block argument count, type, and availability on each incoming edge.
- Return type agreement and the absence of values on void returns.
- Source line and column metadata must be supplied together.

The verifier computes CFG reachability and iterative dominator sets. It rejects unreachable blocks and values that do not dominate a control-flow join.

## Initial constant-folding pass

The public optimizer entry points are \`yir_optimize_function\` and \`yir_optimize_module\`. The initial pass folds scalar integer addition, subtraction, multiplication, division, modulo, negation, integer comparisons, and boolean negation when all operands are known constants. It uses checked arithmetic and does not fold signed-overflow cases, division by zero, or \`INT64_MIN / -1\`; the defined \`INT64_MIN % -1 == 0\` case may be folded. Constants are propagated only from verified SSA definitions that dominate their uses, including definitions in blocks stored later in the function's block array. Block parameters are not assumed constant. The pass verifies its input and its output, and module optimization retains direct-call symbols and validates the complete call graph. f64 folding is deliberately conservative: finite normal constants are propagated, and finite normal addition/subtraction/multiplication/division, unary negation, and comparisons may fold. The sign of zero is retained for unary negation. Division by +0.0 or -0.0 is never folded; overflow to infinity, subnormal results, and possible underflow-to-zero multiplication/division remain runtime operations. Non-finite constants are rejected by the verifier, and NaN/infinity propagation and the complete cross-backend IEEE-754 contract remain open.

The developer-only ylang emit-mir-opt command runs the same frontend and lowering as emit-mir, verifies the whole module, then runs the default ordered pipeline: conservative constant folding, constant-branch simplification with unreachable-block removal, safe local common-subexpression elimination, and dead-code elimination. Each pass verifies its input/output. DCE retains calls and checked operations that can fail at runtime, including integer arithmetic/division/modulo/negation and floating-point division. The ylang emit-ir-c-opt command applies the same optimizer before writing C through the IR backend. Both expose the same conservative f64 folding rules and retain operations that can trap or depend on unspecified IEEE-754 edge behavior. The plain emit-mir and emit-ir-c commands remain unoptimized reference paths, and the production build path is unchanged.

## Remaining work before frontend integration

This IR is not ready to replace the current AST-to-C path. Full calling-convention and ABI metadata, source spans, complete IEEE-754 edge-case policy, explicit float/integer conversions, float formatting and I/O, string operations, memory and aggregate operations, external and indirect calls, stable cross-build symbol IDs and linker-visible symbol mangling for imported functions, ownership/drop metadata, debug locations, and complete frontend lowering for the supported language are still required; current source locations cover lowered instructions, not every IR entity. A first developer-only IR-to-C text emitter now handles the verified scalar subset: i64/f64/bool/void signatures, integer constants and checked arithmetic (`+`, `-`, `*`, `/`, `%`, and general unary negation), f64 constants/arithmetic/comparisons, integer comparisons, boolean and f64 negation, branches with block-parameter copies, direct typed calls, and returns. It uses standalone encoded C identifiers and reproduces checked integer overflow failures for addition, subtraction, multiplication, division (`INT64_MIN / -1`), and negation (`-INT64_MIN`), as well as division/modulo-by-zero behavior. The modulo edge case `INT64_MIN % -1` returns zero, matching the existing runtime. Floating-point division rejects positive and negative zero denominators with the current runtime diagnostic; finite literal constants are accepted and non-finite literals are rejected. NaN propagation, infinity/overflow behavior, subnormal policy, and explicit float/integer conversion rules still need a cross-backend contract. `ylang emit-ir-c <file.yl> -o generated-ir.c` runs the frontend, lowers and verifies the entire module, then writes the generated C through a temporary stream so failed lowering or emission does not leave a partial output file. The command is developer-only and is not wired into the production `build` path. A compile/run regression test has been added; its CI result is still pending. Backends must consume the same verified IR before the architecture can be considered integrated. The `emit-mir` CLI command is a developer inspection path only; normal `build` and `emit-c` still use the established AST-to-C pipeline.

## AST lowering scope

`yir_lower_function` currently accepts `int`, `float`, `bool`, and `void` functions with zero or more scalar `int`, `float`, or `bool` parameters. It lowers initialized scalar locals, simple name assignments, nested `if` / `else if` / `else` (including omitted `else`), and scalar SSA value merges at conditional joins. It also lowers `while`, `for`, unconditional `loop()`, `break`, and `continue`, with typed block parameters for loop-carried values. Boolean `and` / `or` use short-circuit CFG lowering: the right-hand expression is only emitted in the path where its value is required, and the result is merged through a typed boolean block parameter. Direct user-function calls are supported when all parameters are scalar `int`, `float`, or `bool` and the return type is `int`, `float`, `bool`, or `void`; this includes nested and imported calls, float-returning calls, bool-returning calls in conditions, and void calls as statements. Calls carry a module-qualified symbol derived from the callee's canonical source path, and module verification resolves that symbol across the full loaded program. Builtins, indirect calls, external ABI calls, and non-scalar call signatures remain unsupported. The imported-module fixture covers same-named functions in separate source files, transitive imports, and a root module invoking both. Integer expressions support integer literals, negative literals, general unary negation, `+`, `-`, `*`, `/`, and `%`, plus supported direct calls. The initial f64 subset supports finite float literals, scalar float names, float parameters/returns, initialized float locals, simple assignments, unary negation, `+`, `-`, `*`, `/`, matching-type comparisons, and direct calls. Mixed int/float arithmetic is rejected until explicit conversion rules are implemented; non-finite float literals are also rejected. Conditions support boolean literals, scalar bool names, negation (`!` / `not`), integer and float comparisons (`==`, `!=`, `<`, `<=`, `>`, `>=`), short-circuit logical `and` / `or`, and bool-returning direct calls. Global variables, arrays, compound assignments, uninitialized locals, and other unsupported statements or expressions fail explicitly; they are not silently translated. The resulting function is immediately passed through the function verifier. The `emit-mir` driver also runs the module verifier after every function has been lowered, so direct calls must resolve uniquely within the loaded program. `yir_destroy_function` releases the allocated IR storage.

## Textual IR output

`yir_print_function(FILE *, const YIRFunction *)` writes a stable, human-readable dump of function signatures, typed block parameters, instructions, branch arguments, and available source locations. `ylang emit-mir-opt <file.yl>` additionally runs the verified integer/boolean constant-folding pass before printing; f64 instructions are preserved unchanged. `ylang emit-mir <file.yl>` runs the existing frontend and semantic checker, lowers every function in the loaded program, verifies each function and the resolved direct-call graph, and then prints the MIR to standard output. It rejects `-o`; unsupported functions produce a source-located error and no partial MIR output. The command currently works only when every function is inside the documented initial scalar lowering subset.

## Build and tests

Run `make ir-unit-test ir-lower-unit-test ir-print-unit-test ir-c-unit-test` or `sh tests/run-ir-unit.sh`. The full `make test` suite exercises the `emit-mir` and `emit-ir-c` CLIs. Verifier tests cover arithmetic and return, same-block ordering, cross-block dominance, unreachable blocks, invalid joins, typed block-parameter joins, module-level direct-call resolution, finite f64 constants, mixed numeric-type rejection, and f64 arithmetic/comparison contracts. The C emitter unit tests cover scalar integer and f64 arithmetic, checked integer division/modulo/negation helpers, floating-point division checks, direct calls, conditional branches with block parameters, and explicit rejection of unsupported pointer signatures. CLI compile/run fixtures check division-by-zero, `INT64_MIN / -1`, negation overflow, `INT64_MIN % -1 == 0`, and a finite-f64 program with float parameters, return values, arithmetic, negation, comparisons, and direct calls. The emitter is exercised through the yir_emit_c_module API and the developer-only emit-ir-c and emit-ir-c-opt CLIs. Compile/run fixtures cover arithmetic, checked division/modulo/negation failures, f64 arithmetic, short-circuit boolean expressions, nested control flow, direct calls, imported modules, and transitive calls with duplicate source function names. The optimized C path has dedicated tests for safe constant folding and preservation of division-by-zero failures. A differential test runner builds each shared-subset fixture through three paths—the reference AST-to-C path, ordinary IR-to-C, and optimized IR-to-C—then compares exit status, stdout, and stderr, including the initial f64 fixture; the CI result remains validation-pending. Lowering tests cover scalar int/f64 values, f64 parameters/locals/assignments/calls, nested conditional joins, omitted `else`, `while`, `for` increment blocks, unconditional loops, loop-carried values, `break` / `continue`, nested direct function calls, boolean-returning calls in conditions, float-returning calls, void calls as statements, and short-circuit `and` / `or`. CLI regressions compile and run imported calls across transitive modules and short-circuit expressions whose skipped branches contain division by zero. Module verifier tests cover successful call resolution, missing callees, signature mismatch, and ambiguous function names, alongside integer, f64, and boolean values and explicit rejection of unsupported statements. Frontend integration tests parse and semantically check real YLang source before lowering its function AST.


## Machine-readable JSON output

`ylang emit-mir-json <file.yl>` lowers and verifies the complete loaded module, then writes one JSON document to standard output. The top-level object uses format identifier `ylang.mir` and schema version `1`. It contains a `functions` array; each function carries its name, optional module-qualified symbol, return type, typed parameters, and ordered basic blocks. Each block contains typed parameters and ordered instructions. Instruction records preserve opcode names, result and operand IDs, result types, integer or floating constants, branch destinations and edge arguments, direct-call names/symbols and scalar parameter types, and optional source line/column metadata. Missing optional values are JSON `null`, while argument and parameter collections are always arrays. Strings are escaped as JSON strings, and negative floating zero is written as `-0.0` so its sign is not discarded by JSON parsers that distinguish integers and floating-point values. The writer verifies the whole module before emitting any bytes and reports stream failures.


The optimizer API also exposes `yir_run_opt_pipeline` and the ordered pass IDs `YIR_OPT_CONSTANT_FOLD`, `YIR_OPT_SIMPLIFY_CFG`, `YIR_OPT_COMMON_SUBEXPRESSION`, `YIR_OPT_COPY_PROPAGATION`, `YIR_OPT_ALGEBRAIC_SIMPLIFY`, and `YIR_OPT_DEAD_CODE`. Callers can select a subset or order; unknown pass IDs are rejected. Common-subexpression elimination is scoped to one basic block, rewrites every later SSA use including branch-edge arguments, and deliberately excludes checked arithmetic, floating-point division, and calls. The default `yir_optimize_function` sequence runs six ordered passes: constant folding, constant-branch/CFG simplification, local common-subexpression elimination, identical block-argument copy propagation, safe integer algebraic simplification, and dead-code elimination. CFG cleanup uses the verified branch targets and preserves the chosen edge arguments when replacing a constant conditional branch. Dead-code elimination traces live SSA values back through operands and branch-edge arguments, while retaining calls and operations that can trap.


## Verifier robustness and fuzzing

The verifier rejects metadata that does not belong to an instruction kind: call metadata is call-only, and edge-argument metadata is restricted to branch terminators. It checks call argument arity and backing arrays before reading operands, and validates both true and false branch-edge storage before following arguments. `tests/ir_fuzz_smoke.c` generates bounded arbitrary IR shapes with valid in-process backing arrays, runs 4,096 deterministic smoke inputs, and checks block/value count overflow cases. The same input entry point can be compiled with libFuzzer (`make fuzz-ir`) for longer ASan/UBSan-guided runs.


## Explicit numeric conversions

The typed IR represents `to_float(int)` as `i64.to_f64` and `to_int(float)` as `f64.to_i64`. The verifier checks both source and destination types. The C backend emits a standard integer-to-double cast and uses a checked helper for float-to-integer conversion: non-finite values and values outside `[-2^63, 2^63)` fail with the same runtime diagnostic as the AST backend; accepted values truncate toward zero. The optimizer folds only conversions whose constants are statically representable, leaving out-of-range conversions as runtime checks. The conversion fixtures are run through AST-to-C, IR-to-C, and optimized IR-to-C parity paths.


Copy propagation removes a block parameter only when every incoming true and false CFG edge supplies the exact same SSA value. It rewrites uses, removes the corresponding argument position from each predecessor edge, and compacts the target parameter list. Joins with differing incoming values (including loop-carried values) remain unchanged.

Integer algebraic simplification currently handles adding/subtracting zero, multiplying by zero or one, dividing/modulo by one, and reflexive integer comparisons. It does not apply floating-point identities, where NaN and signed-zero semantics would make familiar rewrites unsafe. Checked divisions/modulo by zero and other potentially trapping operations are not rewritten away.
