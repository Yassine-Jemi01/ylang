# YLang 2.3 vs C — Initial paired benchmark results

Date: 2026-11-09

This is the first completed 30-sample paired run of the benchmark suite on a GitHub-hosted Linux runner. It is an initial data point, not a universal performance claim.

## Environment

- YLang: 2.3.0
- Commit: 11f0683cdd42188aa51ade13c95852c7ce08fafa
- Host: Linux x86_64 (Ubuntu runner)
- CPU: AMD EPYC 7763 64-Core Processor
- Native compiler: GCC 15.2.0
- Optimization: -O2 for both implementations
- Samples: 30 measured + 5 warm-ups per executable
- Timing: wall-clock process execution including startup and exit
- Every run's stdout was checked for exact equality.

## Results

| Workload | YLang median | C median | YLang/C | Interpretation |
|---|---:|---:|---:|---|
| Integer arithmetic (10M iterations) | 60.238 ms | 44.660 ms | 1.3488x | YLang 34.9% slower |
| Conditional branches (10M iterations) | 60.016 ms | 62.113 ms | 0.9662x | YLang 3.4% faster in this sample |
| Array indexing (20M iterations) | 12.548 ms | 7.630 ms | 1.6446x | YLang 64.5% slower |
| Function calls (10M calls) | 47.713 ms | 47.727 ms | 0.9997x | Effectively tied |

## Interpretation and limits

The C programs are direct native implementations; the YLang programs are compiled through YLang's C backend. Both use GCC, -O2, and matching hardening flags. The generated YLang executable includes its runtime, so this measures the practical C-backend executable rather than only isolated generated instructions.

The array workload uses YLang's array representation and a fixed-size C array. It measures end-to-end indexing behavior and should not be interpreted as a pure load-instruction comparison.

These results do not establish that YLang is generally faster or slower than C. They show that this set of workloads is close in function-call overhead, competitive in branching, and slower in arithmetic and array indexing. Repeat on another runner and representative local hardware before treating small differences as meaningful.
